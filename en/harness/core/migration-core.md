## Always Do This When Starting Work

1. Read `<project>-migration-*/03-worklog/session-context.md` to confirm the state from last time
2. **On the first session, run the startup interview** (below). Not needed from the second session on
3. Read the procedure document appropriate to the current Phase:
   - Phase 0-2: `00-analysis/analysis-procedure.md` / Phase 3 onward: the relevant Step in `01-plan/work-plan.md`
4. Confirm the gate applicability with `./verify.sh status` (from Phase 3 onward also run `./verify.sh`)

### Startup Interview (first session only)

Do **not** make the human fill in every `<PLACEHOLDER>` in `migration-project.md`. Fill them in this order:

1. **Lightly scan the source tree and fill in what you can** (migration target name, repository layout,
   current stack, build system, location of test assets). Do not dig deep — detailed structural analysis
   is left to ATX in Phase 0a
2. **Ask once, as a single bulleted list, only for the items you could not fill in.** Do not ask piecemeal
3. **Attach a provenance marker to every value**: `⟨confirmed⟩` (confirmed by the user) /
   `⟨inferred⟩` (inferred by the AI).
   **An `⟨inferred⟩` value is a hypothesis (CP-3) and must not be used as a premise for an ADR or the work-plan**.
   Confirm mandatory input before 0a-3 and derived information before the work-plan is confirmed (otherwise `./verify.sh project` FAILs)
4. **The target stack may stay undecided.** It is decided as an ADR in Phase 0b after seeing the
   analysis. All you need to start is "the root path of the source tree" and the "off-limits" list

Also confirm **first** whether existing ATX analysis results exist (Phase 0a-0). If they do, enter the
approach of using the existing results and **skip the git preparation, transform-config creation, and
ATX execution (0a-3/0a-4/0a-5) entirely**. Not knowing the commit the analysis saw is the default; do
not stop to confirm it (it is covered by the Phase 2 corroboration — CP-3).

## Behavioral Discipline — Tier Gates (Stages of Autonomous Execution)

Classify all work into one of three Tiers (stages) according to **rollback cost and the value of
building human understanding**. Migration is exploratory work, and deepening the human's understanding
through the work is itself part of the purpose. Phase gates are both risk management and a place where
humans digest and form understanding.

### Tier 0 — Autonomous Execution Zone (continue without confirmation)

Execute and continue without confirmation for work that satisfies all of the following:
- Work within a Step already recorded in the work-plan (code fixes, builds, tests, investigation)
- `./verify.sh` stays all-PASS (or work is in progress toward all-PASS for that Step)
- Does not match a HOLD trigger (below)

### Tier 1 — Asynchronous Review Zone (execute without stopping, but leave a record)

Execute the following without waiting for a user instruction (the human batch-reviews later via
worklog / git log):
- Updating worklog / session-context, appending knowledge (CP/DP)
- Commits and pushes to the records repository, and commits of verified fixes to the modernized tree
- **Transitions between Steps within Phase 3**: after displaying the completion report + a preview of
  the next Step + the LL/CP/DP inventory review result, continue if the following are satisfied:
  - All 3 verify stages (build/smoke/integration) are PASS
  - **The smoke gate is implemented** (proceeding to Step 2 or later with it still unimplemented is
    prohibited; implement it upon completion of Step 1)
  - Does not match a HOLD trigger

### Tier 2 — Stop-and-Confirm Zone (HOLD. Stop and defer to human judgment)

Always stop when any of the following mechanical triggers (HOLD triggers) is met. Do not loosen the
criteria on your own judgment:

| # | Trigger | Judgment material to provide when stopping |
|---|---------|----------------------|
| HOLD-1 | Exclusion, disabling, or stubbing of a feature (a change involving loss of functionality) | Exclusion flow + ADR draft (skills/migration-adr) + independent verification (a per-item second opinion; skills/migration-adversarial-review) |
| HOLD-2 | A change touching a wire format, a persisted data format, or an externally exposed interface | Compatibility impact analysis + ADR draft |
| HOLD-3 | A change to the expected list (success criteria) in verify.sh = a scope change | Reason for the change and the diff against the work-plan |
| HOLD-4 | The hypothesis log for the same issue reaches 3 lines unresolved, or spans 2 sessions | The full hypothesis log + possibility of misdiagnosis + a subtask proposal |
| HOLD-5 | A substantial chunk of additional work not in the work-plan arises | A proposal of "Start subtask: \<taskname\>" |
| HOLD-6 | A destructive operation, a change to a shared environment, or **stopping a long-running job (analysis, build) that is in flight** | The action and its scope of impact (ask the user to run it manually) |
| HOLD-7 | An ADR-equivalent design decision (a choice that imposes a lasting constraint going forward) | ADR draft (lightweight stop protocol) |
| HOLD-8 | Crossing a Phase boundary (0a→0b→1→2→3→4) | Phase completion criteria check + standard Phase-gate confirmation + the LL/CP/DP inventory review result + the result of the **detector negative tests** (CP-13. Independent verification is **limited to the migration completion declaration and the HOLD-1 feature exclusion**; skills/migration-adversarial-review) |

- **When the interpretation of an instruction extends to an irreversible or high-cost operation,
  confirm the interpretation before acting.** "Do not use the result" does not mean "you may stop the
  generation". Motives such as saving cost or returning to a branch are the agent's own convenience, not
  the user's request (the classic case of a well-meant optimization overstepping the instruction)
- **HOLD-7 judgment criteria**: "If this were changed in the future, would it ripple beyond a single
  code fix?" "Would a future maintainer ask 'why'?" — if either is Yes, it is ADR-equivalent.
  **When in doubt, write an ADR and stop. Writing too many is not a fault**
- **Lightweight stop protocol**: Present an ADR draft (background / options / proposed decision /
  impact). The user can approve with a single word. **While a decision is pending, you may proceed with
  other work that does not depend on it**. Pending decisions are managed in the Decision Queue in session-context
- Details of the HOLD-1 exclusion flow / HOLD-8 standard Phase-gate confirmation: see **skills/migration-adr**
- If Tier 2 (HOLD) fires frequently (3 or more times in a single Step), that is a sign the criteria are
  too broad. Propose an adjustment to the user

### Model Assignment (vary it along the Tiers)

**What you split on is not "primary/secondary" but "judgment/volume". A sub-agent does not mean a lighter model.**

| Target | Dominant property | Assignment |
|------|------------|---------|
| Tier 0 work (implementation, builds, tests, investigation within the work-plan) | Volume | A faster model is fine |
| Tier 1 work (worklog, records, commits, translation, transcribing ledger rows) | Volume | **A faster model is recommended** |
| **All of Tier 2 (HOLD), ADR decisions, HOLD-1 exclusions, confirming the work-plan, independent verification** | Judgment | **Keep the stronger model** |

The independent-verification sub-agent is exercising judgment, so it gets the stronger model; the
translation batch gets the faster one. **Migration incidents happen not from "we could not write a lot
quickly" but from "we failed to notice a discrepancy against the primary source".**
If you drop the model, first confirm that what you are dropping contains no judgment.

## Work Quality Rules (always apply)

1. **AI analysis results are hypotheses.** Corroborate against the real code before including them in the plan (CP-3)
2. **A successful build ≠ a completed fix.** Do not declare completion until it is observed via a runtime test (CP-4)
3. **Before fixing, define "what must be observed for this to be correct"** (CP-4)
4. **After making one fix, re-verify all the way through to final success** (CP-2)
5. **Corroborate platform-dependent configuration values against primary sources (official docs, man pages, etc.)** (see the relevant Playbook's practices.md; e.g. DP-8 in the clang Playbook)
6. **For crashes and failures, always check the executed command, the environment, and the exit code** (e.g., 124 = survived a timeout, 139 = SIGSEGV, 127 = missing lib)
7. **Confirm the root cause only through demonstrated causality** (CP-8). Keep writing "hypothesis" until the symptom reproduces/disappears by toggling the cause ON/OFF
8. **Long-running commands (ATX execution, large builds, etc.) are run by the AI, which monitors their logs.** Do not rely solely on a simple liveness-polling loop (details: skills/migration-troubleshooting)

### Hypothesis Log (mandatory during troubleshooting)

Record one line for every fix attempt (small scale = worklog, subtask = investigation.md):

| # | Hypothesis | Prediction (what this fix should change) | Observed result | Verdict (resolved/rejected/ongoing) |
|---|------|--------------------------------|---------|---------------------|

Attempting a fix without recording it is a violation of the recording obligation. Details: **skills/migration-troubleshooting**

### Interruption Resilience (declare before starting)

The recording obligation fires at work completion, so it cannot protect interrupted work. Therefore:
1. **Before the first change**, write a one line into the "In-progress Investigation /
   Working-tree State" section of `03-worklog/session-context.md`:
   `- **This turn (<timestamp>):** <what you are about to do>`.
   Write it even for work within the work-plan. **Get `<timestamp>` by running
   `./03-worklog/turn-report.sh --declare` every turn and using its output as-is. Typing it by hand, or
   reusing/approximating a previous turn's value, is forbidden** (the guard compares it character by character and blocks)
2. **Do not let in-progress state live only in the uncommitted working tree**: make small, frequent
   `[wip]`/`[diag]` commits to the modernized tree, and tag throwaway diagnostic code with `// DIAG-<id>:`
   so it can be removed later
3. **At close-out, copy the declaration line and the hypothesis log into the worklog** (otherwise nothing permanent remains)

Details: **skills/migration-troubleshooting**

## Recording Obligations

Always do the following upon completion of each unit of work (investigation, fix, test). Do not declare
"complete" until you have done so:
1. Append to `03-worklog/worklog.md` (chronological order, append at the end). After appending,
   **run `./03-worklog/turn-report.sh --worklog` and paste the output into that entry** (the raw log is git-ignored).
   **Writing the table by hand or transcribing it is forbidden. The numbers must be the command output as-is**
2. Update `03-worklog/session-context.md` (Current Status / Next Actions / Verification Queue / Decision Queue)
3. Upon completion of a Phase/Step, a subtask, or a Tier 2 (HOLD) response, perform an LL/CP/DP inventory review (state explicitly if none apply)

Formatting details (commit messages, appending knowledge, timing of inventory reviews): **skills/migration-recording**

### Reference Granularity and Volume of Knowledge (keep the context small)

- **By default read only the summary table of the knowledge files (practices-common.md / practices.md).**
  Open the body when you hit the relevant theme. The body is the layer humans read to understand, so it may be detailed
- **Do not read `worklog.md` chronologically.** Recover the previous state from `session-context.md`
- **Do not assign an unprefixed `CP-N` / `DP-N` on the project side** (use `CP-<project>-N` / `DP-<project>-N`)
- The volume limits (summary rows, body line count, number of entries) are mechanically checked by
  `./verify.sh knowledge`. Exceeding a limit is a trigger for consolidation; deciding not to consolidate passes as long as it is recorded

### Markers for Temporary Changes (mechanically detected)

A change that must exist only temporarily always gets a marker before it is committed.
`./verify.sh repo-sync` detects a marker left in committed code as a FAIL:

| Marker | Purpose | Condition for clearing |
|---------|------|-----------|
| `// DIAG-<id>:` | Throwaway diagnostic code | Revert it after the cause is confirmed |
| `// STUB-<id>:` | A temporary stub, mock, or disabled feature | Put the implementation in. For a permanent exclusion, write an ADR as HOLD-1 and set the adaptation-ledger disposition to "not required (reason mandatory)" |

**This is a mechanism to mechanically close off the "unintentionally mocked a feature and never noticed to the end" failure.**
The forbidden patterns the Playbook defines (`not implemented`, etc.) are checked by the same gate.

## Verification Gate

- Do not record "complete" until `./verify.sh` is all-PASS. **All 8 gates**:
  - Four whose application is switched on work-plan confirmation: build (artifacts exist) → smoke (starts up) →
    integration (interoperation, golden-path E2E) + nonfunc (non-functional), when opt-in
  - **Four that always apply**: repo-sync (two-repository sync, diagnostic/stub markers) →
    knowledge (knowledge volume) → adaptation (adaptation ledger) → project (provenance markers)
- Applicability can be checked with `./verify.sh status`
- **Register all in-scope deliverables into the expected list when the work-plan is confirmed (on day one)** (CP-7. Register even unbuilt ones)
- Promote ad hoc verification into `02-test/integration/` and invoke it from the integration gate
- Details and the rules for test records: **skills/migration-verification**

## Subtasks

When the user instructs "Start subtask: \<taskname\>", or when a proposal under HOLD-4/HOLD-5 is approved,
follow the procedure in **skills/migration-subtask**. Place all working files inside the subtask directory.

## Session-End Checklist (Tier 1 · Asynchronous Review Zone — execute without waiting for instruction)

Execute this at session end without waiting for instruction. **Committing/pushing only one of the repositories is incomplete**:
1. Confirm the worklog entry → 2. Update session-context (including the repository sync status table)
3. Commit the records repository until clean → 4. Commit verified changes to the modernized tree
5. If a remote exists, push both → 6. Report `git log --oneline -1` and `git status --short` for both repositories
Details: **skills/migration-session**

## Off-limits / Project-Specific Information

Refer to `migration-project.md` (Kiro: `.kiro/steering/` / Claude Code: top of `CLAUDE.md`).

**Do not change the content of the source tree** (initializing its history is permitted). Do the work on
the modernized tree side (skills/migration-tree-setup). Only the following three git operations are
permitted against the source tree:

- `git init` / the initial commit / adding `.gitignore` (because ATX requires git management)
- Forbidden: adding a remote / push / reset / rebase / deleting branches / force operations. When in doubt, HOLD-6

Running ATX writes to the target repository (`.gitignore` append, creating a staging branch, committing).
**Record the branch and HEAD before the run and confirm they match after the run** (record in `00-analysis/analysis-runs.md`).
