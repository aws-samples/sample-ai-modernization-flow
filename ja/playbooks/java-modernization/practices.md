## DP-1: 検証コマンドは test-compile を含める

### 目的
クラス削除を伴う変換（レガシー機能除去等）で、`src/test/java/` 配下の対応テストファイルが
残存してコンパイルエラーになる事故を、変換の検証段階で検出する。

### ルール
1. verify の build ゲートの検証コマンドは
   `mvn clean install -DskipTests` を使う（`JAVA_HOME` の明示指定を含める）
2. `mvn clean compile` を検証コマンドにしない:

   | コマンド | メインコード | テストコード | テスト残存の検出 |
   |---------|:---:|:---:|:---:|
   | `mvn clean compile` | ✅ | ❌ | ❌ |
   | `mvn clean test-compile` | ✅ | ✅ | ✅ |
   | `mvn clean install -DskipTests` | ✅ | ✅ | ✅ |

3. クラス・インターフェースを削除する変換では、work-plan の Step に明示する:
   「対応するテストクラスも必ず削除すること」+ 検証「`grep -r "削除クラス名" src/test/`」

### チェック方法
- verify.sh の BUILD_CMD が `install -DskipTests`（または `test-compile` 以上）になっている

### アンチパターン
- ❌ `mvn clean compile` で「ビルド成功」と判定する
- ❌ JAVA_HOME 未指定でシステムデフォルトの別バージョンJDKでビルドしてしまう

### 実例
OAuth 1.0 / XML-RPC / CSRFフィルター削除の3変換すべてで、テストファイル残存による
コンパイルエラーが変換後に発覚した。検証コマンドを `install -DskipTests` に改善して解消。

## DP-2: セキュリティデフォルト変更のサイレント障害を疑う

### 目的
フレームワークのメジャーアップグレードで導入されるセキュリティ強化デフォルトは、
**例外もエラーログも出さずに機能を無効化する**ことが多い。「動かない」ではなく
「例外なく空になる・不発になる」症状に対して、正しい原因系を最初から仮説に含める。

### ルール
1. フレームワークアップグレード後、以下の症状は**セキュリティデフォルト変更を第一仮説**にする:
   - 動的コンテンツ・タイトルが空文字でレンダリングされる（例: Struts OGNLアローリスト）
   - フォームパラメータがActionにバインドされない/NPE（例: `struts.parameters.requireAnnotations`）
   - ファイルアップロードが例外なく不発（例: Struts 7 `UploadedFilesAware` API移行）
2. 診断ログを有効にして観測する（仮説ログの観測列に使う）:
   例: `struts.ognl.logMissingProperties=true`
3. 対応方針は「デフォルト無効化」（設定で旧動作へ）か「新API準拠」（アノテーション付与・
   アローリスト整備）かを選び、理由をADRに記録する（本番向けは新API準拠を推奨）
4. これらは公式マイグレーションガイドに記載されている（CP-9を先に実施していれば予防できる）

### チェック方法
- E2Eテストにページタイトル・動的コンテンツの**非空アサーション**が含まれている
- ファイルアップロード等の副作用系機能に「結果の存在確認」テストがある（サイレント障害の検出）

### アンチパターン
- ❌ ログにエラーがないことを根拠に「問題なし」と判定する
- ❌ コンパイル成功とユニットテスト通過でアップグレード完了と宣言する（CP-4）

### 実例
Webフレームワークのメジャーアップグレードで (1) サーバサイド式言語のアローリストによりページタイトルが空 (2) パラメータバインド必須アノテーションの導入
によりユーザー登録がNPE (3) アップロードAPIの変更でメディアファイル保存が例外なく不発、の
3種のサイレント障害が発生。いずれも公式ガイド記載事項だった。

## DP-3: CSRF 有効化はフォーム全数調査とセットで行う

### 目的
Spring Security CSRF等の有効化は「設定1行」に見えるが、実際にはアプリ内の**全POST経路**への
対応が必要。漏れは 403 Access Denied として実行時にのみ発現する。

### ルール
1. 有効化前に POST フォームを全数列挙する: `grep -rn '<form.*method="post"' --include='*.jsp' -i`
   （JSPだけでなくVelocity/Thymeleaf等の全テンプレートエンジンを対象に）
2. 特に漏れやすい経路を個別確認する:
   - **ログインフォーム**（メインアプリと別のJSPにあることが多い）
   - **匿名ユーザーのPOST**（コメント投稿等。トークンを持てないため除外が必要）
   - **multipart/form-data**（CsrfFilterはボディからトークンを読めない → URLクエリパラメータ方式）
3. パス除外は `security="none"` に頼らない（フィルターチェーン全体が無効になり認証情報も消える。
   FORWARD ディスパッチではマッチングも信頼できない）。`<csrf request-matcher-ref>` +
   `AndRequestMatcher` で「デフォルトのHTTPメソッドフィルタ再現 + パス除外」を組む
4. `request-matcher-ref` は**デフォルトのGET/HEAD/TRACE/OPTIONS除外を完全に上書きする**ことに注意

### チェック方法
- E2Eテストが「ログイン → 認証必須ページ → フォーム送信 → 匿名POST（該当あれば）→
  ファイルアップロード」を全て通す

### アンチパターン
- ❌ CSRF設定を有効化してGETでの画面表示だけ確認して完了とする
- ❌ hidden field 方式を multipart フォームにも適用する（読み取られない）

### 実例
ログインフォーム（403）、匿名コメント投稿（4回の試行錯誤の末 AndRequestMatcher で解決）、
メディアアップロード（クエリパラメータ方式）の3系統でCSRF対応漏れが実行時に発覚した。

## DP-4: E2E はフレームワーク生成IDに依存しないセレクタを使う

### 目的
UIフレームワーク（Struts タグ等）が生成するHTML要素IDの生成アルゴリズムはメジャーバージョンで
変わる。生成IDをハードコードしたE2Eセレクタは、アップグレードのたびに壊れる。

### ルール
1. セレクタの優先順位: `data-*` 属性 > 安定したCSSクラス+属性 > 手書きID > 生成ID（最終手段）
2. フレームワークのメジャーアップグレード後は、タグ生成要素（submit/link/input等）の
   ID変化を監査する
3. CSSフレームワーク移行（Bootstrap等）ではレイアウト変化でボタンがビューポート外に
   出ることがある。クリック前の `scrollIntoView` をPage Objectの共通処理にする
4. モーダル等のJS連携UIは、フレームワークのAPI変化（jQuery→ネイティブAPI等）と
   DOM配置制約（stacking context）を確認する

### チェック方法
- E2Eコードに生成ID形式（例: `entry_%{...}` のようなテンプレート込みID）のセレクタが残っていない

### アンチパターン
- ❌ 現行バージョンの生成IDをそのままセレクタにコピーする
- ❌ ヘッドレス実行の解像度・ロケールを固定せずにテストする
  （ロケールはJVMデフォルトが使われる: `MAVEN_OPTS="-Duser.language=en -Duser.country=US"`）

### 実例
Webフレームワークのメジャーアップグレードで送信ボタンの生成IDが変わり、対象ボタンが
セレクタで見つからなくなった。安定したCSSクラス+属性セレクタへ変更して解決。CSSフレームワークの
メジャーアップグレードによるレイアウト変化によるクリック遮断は `scrollIntoView` で解決。

## DP-5: UI描画型アプリの integration ゲートには実ブラウザの golden-path E2E を必ず含める【必須】

**本項は推奨ではなく必須である。** `verify.sh` の `REQUIRE_GOLDEN_PATH=1` と
`GOLDEN_PATH_TESTS` への登録で機械的に強制する（未登録なら integration ゲートが FAIL する）。

Web UI を持つ移行では、build/unit/smoke だけでは UI 層の silent failure（例外なし・HTTP 200 で描画が空/不可視）を
捕捉できない。実ユーザーが必ず通る動線（登録→ログイン→主要CRUD、可能なら画像アップロード→挿入→表示→コメント等）を
**実ブラウザ（Selenium 等）で通す E2E** を早期に integration ゲートへ組み込む。build/unit/smoke だけを「検証」と呼ばない。
（診断則・観測の妥当性は practices-common.md の CP-8 を参照。UI 不具合はブラウザ DevTools 相当で実測する。）
