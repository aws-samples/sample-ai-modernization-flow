# Java モダナイゼーション考慮事項

フレームワーク・ランタイムのメジャーアップグレードを伴う Java モダナイゼーションの
ドメイン知見集。レガシーJavaアプリケーション移行（Java 11→21, Struts 2.x→7.x, Spring 5→6,
Jakarta EE 10, Bootstrap 3→5）の実績から蒸留した。

## 1. 移行先スタックの選定（Phase 1 — CP-10）

- **EOL/LTS確認**: Java LTS（17/21/25...）、フレームワークのサポート期限を表にする
- **互換マトリクス**: 「Struts 7.x → Jakarta EE 10前提」「Spring Security 6.x → Spring 6.x必須」
  「Spring 6.x → Jakarta EE 9+必須」のような連鎖を列挙し、矛盾がないことを確認する
- **多段ジャンプの扱い**: メジャー2段以上のジャンプは破壊的変更が累積する。
  公式ガイド（境界ごとに複数存在 — CP-9）から破壊的変更を数え、影響ファイル数と掛けて
  コストを見積もり、段階実施か一括かを判断する

## 2. 名前空間・API移行の定番

| 項目 | 内容 |
|------|------|
| javax → jakarta | Jakarta EE 9で名前空間が全面変更。import・web.xml・TLD・設定ファイルに波及 |
| Servlet コンテナ | Jetty 12はEE8/9/10でアーティファクトが分かれる（`org.eclipse.jetty.ee10.*`）。Tomcat 10.1+=EE10 |
| メール | `javax.mail` → `jakarta.mail-api` + 実装（angus-mail） |
| 接続プール | commons-dbcp → commons-dbcp2 |
| SLF4J 1.x → 2.x | バインディング機構が変更（ServiceLoader方式） |

## 3. セキュリティ強化デフォルトとサイレント障害（DP-2）

モダンフレームワークはセキュリティ制限をデフォルト有効にする方向に進化しており、
**旧コードは例外なくサイレント障害として動かなくなる**。既知のパターン:

| 症状 | 原因の例 | 検出方法 |
|------|---------|---------|
| 動的コンテンツが空文字 | 式言語のアローリスト（Struts OGNL） | E2Eの非空アサーション + 診断ログ |
| フォーム値が入らない/NPE | パラメータバインドのアノテーション必須化 | フォーム往復のE2E |
| アップロードのサイレント障害 | ファイルアップロードAPIの世代交代（旧setterが呼ばれない） | 結果の存在確認 |
| 403 Access Denied | CSRF有効化とフォーム対応漏れ | 全POST経路のE2E（DP-3） |

## 4. Spring Security CSRF の落とし穴（DP-3）

- ログインフォームは別JSPにあることが多く漏れやすい
- 匿名ユーザーのPOST（コメント等）はトークンを持てない → パス除外が必要
- `security="none"` は認証情報ごと消え、FORWARDディスパッチで信頼できない
- `<csrf request-matcher-ref>` はデフォルトのメソッドフィルタを**完全上書き**する
  → `AndRequestMatcher` で「NOT(GET|HEAD|TRACE|OPTIONS) AND NOT(除外パス)」を組む
- multipart/form-data は hidden field のトークンをフィルタが読めない
  → action URLのクエリパラメータ方式（共通ヘッダにJSを1つ置けば全フォーム対応可能）

## 5. E2Eテスト基盤の移行（baseline モードC = 既存テストを流用）

既存のSelenium E2Eがある場合、それをモダンスタックで動かすこと自体が移行作業の一部:

- コンテナプラグインのEE対応版への更新、WARオーバーレイでは `start-war` ゴール
- JNDIリソースは `WEB-INF/jetty-env.xml`（コンテキストにより `jettyXmls` は無視される）
- WebDriver: ヘッドレスChrome（`--headless=new --no-sandbox --window-size=1920,1080 --lang=en-US`）
- **ロケール**: サーバー側i18nはJVMデフォルトロケールで解決される。
  `MAVEN_OPTS="-Duser.language=en -Duser.country=US"` で固定
- セレクタはフレームワーク生成IDに依存させない（DP-4）

## 6. テスタビリティ（変換で新規コードを書く場合）

- 外部SDK統合はインターフェース境界を先に設計する（SDKのfinal型を境界の外に出さない）
- staticメソッド・グローバル状態への依存はテスト時に差し替え可能な形に分離する
- テスト実行環境（JAVA_HOME、Mavenパス）をコーディング前に確認する
- プロダクションコードとテストコードを交互に書く（後からのテスタビリティ修正は二度手間）

## 7. デプロイ環境との相互作用（参考）

ターゲット環境の制約がアプリ改修に逆流することがある。実例:
ローカルファイルベースの検索エンジン（Lucene + ファイルロック）はマルチインスタンス構成
（ECS複数タスク + 共有ストレージ）でインデックス破損リスクとなり、マネージド検索サービス
（OpenSearch）への移行というアプリ改修が必要になった。
デプロイ設計は本フローのスコープ外だが、**マルチインスタンス化の可否**（ローカル状態・
ファイルロック・インメモリキャッシュの有無）は分析段階で把握しておく価値がある。
