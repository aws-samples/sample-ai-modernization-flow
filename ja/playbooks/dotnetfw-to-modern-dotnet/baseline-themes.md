## テストパターン

| テーマ | テストパターン | 参照 |
|--------|--------------|------|
| **静的アセットの配信** | **画像・CSS・JS が実際に 200 で返ることを URL 単位でアサートする。** ページが 200 で描画されるだけでは通ってしまう（`<img>` の 404 は HTML には出ない）。`onerror` のフォールバック先も 404 になりうるので**代替画像も出ない** | MP-7, MP-9, MP-10, DP-8 |
| **関連データの読み込み** | **値レベルでアサートする。** 「注文詳細ページが 200」ではなく「書籍名と価格の文字列が本文に含まれる」。遅延読み込みが既定 OFF になるため、`Include` 漏れは**例外なく `null` / 空コレクション**になり画面だけが空になる | MP-17, DP-5, reference §4-1 |
| **書式（通貨・数値・日付）** | **記号込みの文字列でアサートする。** 「金額が表示される」ではなく「`$` を含む」。既定カルチャがコンテナ環境に依存するため、**書式規則は変わらないのに表示だけ変わる** | MP-12, reference §5-2 |
| **文字列の並び順** | **一覧の並びを固定する。** NLS → ICU で非英数字の扱いが変わる（アポストロフィ・記号・合字を含むデータで差が出る）。実データに該当レコードがあるか先に確認し、無ければ**テストデータに混ぜる** | MP-13, MP-14, reference §2-1 |
| **ページング境界** | **1ページ目と2ページ目に同じ ID が出ないことをアサートする。** `OrderBy` なしの行制限操作は EF Core で安定順序が保証されない。⚠️ **再現しないことがあるので実行時テストだけに頼らない**（静的走査を併用する） | MP-14, MP-19 |
| **認可の既定** | **2方向で固定する。** ① 未認証で保護ルートが認証へリダイレクトされる ② 匿名許可のページが匿名で 200 を返す。②を省くと**過剰に閉じる回帰**を見逃す | MP-1 |
| **入力検証の否定系** | **拒否されることをアサートする。** 上限超過ファイル・禁止拡張子（`.gif` / `.svg` / `.exe`）の POST が拒否される。**正常系のアップロード成功では防御の有無を判別できない。** 静的検査（属性が付いているか）で代替してはならない | MP-2, DP-6, verify-snippets §5 |
| **検証失敗時の再描画** | **不正入力を POST して 500 でないことをアサートする。** モデルを渡さない再レンダリングは、Tag Helper が有効化された後に初めて `NullReferenceException` になる。**正常系だけでは原理的に到達しない** | MP-4, DP-3 |
| **更新 vs 作成** | **既存 1件が更新され、件数が増えないことを ID レベルでアサートする。** `action` を持たない form が現在 URL のルート値に救われている箇所は、「整える」と ID が消えて新規作成になる | MP-5, DP-3 |
| **トランザクション境界** | **副作用を全部数える。** 「注文が作られた」ではなく「注文が作られ、在庫が減り、カートが空になる」の3つを同一コミットで確認する。DI スコープを誤ると主エンティティだけがコミットされる | MP-20 |
| **上書き保護の分岐** | **変更しない属性が保存前後で不変であることを値でアサートする。** 「更新が成功した」では通る。追跡 / detached の変化で「今は不発の分岐」が効き始めるため、**片方の防御を消すとサイレント障害になる** | MP-21 |
| **ボタン経由の遷移** | **状態が実際に変わることをアサートする。** 一覧画面の描画だけでは通る。ルート名の規約変更（`Async` 接尾辞の自動除去）で**画面は正常・ボタンだけ 404** になる | MP-6 |
| **Area ごとのビュー機構** | **Area 配下の画面でも検証サマリ等が描画されることをアサートする。** ビュー共通設定は自フォルダとサブフォルダにしか効かず、Area は別扱いである。ルート直下だけ確認すると Area の未回復を見逃す | MP-3, DP-3 |
| **ネイティブ依存の出力** | **バイト一致比較を採らない。** 寸法・フォーマット・チャンネル数・ファイルサイズの範囲など**知覚的・構造的な性質**でアサートする。同一入力でのバイト一致を保証する一次情報は無く、アーキテクチャ間の差異報告もある | MP-15, reference §6 |
| **現行の壊れ方の固定** | **機能除外を承認した箇所は「壊れたまま」を期待値として固定する。** 例: 「更新すると値が既定に戻る」をアサートする。**その行には承認 ID（ADR）を必ず添える** — 添えないと次の保守者が「バグ」として直し、テストが落ちる | DP-3, HOLD-1 |

## baseline モードの選び方（本ドメインでの注意）

| 状況 | モード | 注意 |
|------|-------|------|
| 現行環境が稼働しており実測できる | A（実機観測） | 最も強い。移行前後の差分を直接取れる |
| **現行環境が無い / テスト資産も無い** | **B（実コードから期待動作を定義）** | 本ドメインで最も多い。下記の落とし穴に注意 |
| 既存テスト資産を流用できる | C | .NET Framework 向けテストがモダン .NET でビルドできるかを先に確認する |

### モードB（コード読解で定義）の落とし穴: 網羅の基準に Razor ビューと設定ファイルを含める

実測で踏んだ失敗を記録する。**モードB（コード読解で定義）の網羅の基準を `.cs` だけにすると、
移行リスクの主要部分が落ちる。**

公開サンプル（AWS の Bob's Used Bookstore）での実測では、当初 `.cs` 129ファイル / 5,722行を網羅の基準としたが、
**Razor ビュー 42ファイル（2,269行）と設定 7ファイル（385行）が抜けていた**。
落ちていたのは具体的に次のものである:

- `ToString("C")` の使用箇所（通貨書式）→ MP-12
- 静的アセットのパス参照 → MP-9
- 旧 Razor ヘルパと `asp-*` の所在 → MP-3
- `<globalization>` 設定の有無そのもの

**正しい網羅の基準は「`.cs` + `.cshtml` + `.config`」である**（実測では 178ファイル / 8,376行）。
`.cs` だけを見ると「.NET Framework への結合はコードにある」という思い込みで進み、
**ビューと設定に集中している結合を見落とす。**

**網羅率を機械で照合する。** 網羅の基準の一覧と、実際に読んだファイルの一覧の差集合を取り、
**未参照ゼロを機械確認する**（精度だけを測って網羅率を測らないのが典型的な失敗である）。

### Web 層を先に読むのは前倒しであって純増ではない

「Web 層まで読むのは重い」と感じるが、**.NET Framework への結合は Web 層に集中している**ため、
Phase 2 の裏取りでいずれも読む必要がある範囲である。**前倒しであって作業の純増ではない。**

## 自動抽出された「業務ルール」を仕様書として使わない

**技術スタック移行では、自動抽出した業務ルールを baseline の出所にしない。**

実測: 4ドメイン42項目を一次コードで裏取りしたところ、記述が正確だったのは **23件（55%）**で、
不足12件・誤り7件だった。**より重いのは精度ではなくスコープの死角である** —
自動抽出が見るのはドメイン層の業務ルールだが、**.NET Framework への結合は Web 層に集中しており、
原理的にそこを見ていない。baseline が最も必要な場所を覆わない。**

**精度は裏取りで救済できるが、網羅率は救済できない。**
抽出結果は参考資料として残してよいが、**期待動作の出所は実コードに置く**。
