## DP-1: イベント駆動I/Oモジュールの設計制約

### 目的
新OS用イベントモジュールを作る際に、アプリケーションコード側の前提を壊さない。

### ルール
1. アプリケーションコードがどのイベントモデルを前提に書かれているか確認してから実装する:
   - 「EAGAINまで読み切る」ループ → エッジトリガ前提
   - 「1回のread/writeで返る」設計 → レベルトリガ前提
   - 「イベント受信後に再登録する」ループ → Event Ports/kqueue型
2. イベントモデル対応表（例: Solaris → Linux）:

   | 移植元 (Event Ports) | 移植先 (epoll エッジトリガ) |
   |---------------------|--------------------------|
   | 再登録必須 | 不要 |
   | event_flags | `USE_CLEAR_EVENT` |
   | add_connection | `EPOLLIN\|EPOLLOUT\|EPOLLET` |

3. レベルトリガを選ぶと `handle_read_event` / `handle_write_event` が `EPOLL_CTL_DEL` を発行し、SSL通信等でレスポンスが返らなくなることがある。

### チェック方法
```bash
# エッジトリガ前提の判定
grep -n 'EAGAIN\|EWOULDBLOCK' src/  # ループ内で使われていればエッジ前提
grep -n 'ngx_handle_read_event\|ngx_handle_write_event' src/
```

### アンチパターン
- ❌ イベントモデルを確認せずに「とりあえずレベルトリガ」で実装する
- ❌ 非SSL通信のテストだけで完了宣言する（SSL通信はイベント再登録の影響を受けやすい）

## DP-2: GCC バージョン差によるビルド互換性の段階的対応

### 目的
古いCコードをモダンGCC (10+) でビルドする際に発生する「以前は通ったが今は通らない」問題を効率的に解決する。

### ルール
1. GCC のメジャーバージョンアップで変更されたデフォルトを事前に把握する:

   | GCC版 | 変更 | 影響 | 暫定回避フラグ |
   |-------|------|------|--------------|
   | 10+ | `-fno-common` がデフォルト | ヘッダ内グローバル変数定義で multiple definition エラー | `-fcommon` |
   | 14+ | `-Werror=implicit-function-declaration` | 宣言なし関数呼び出しがエラー | `-Wno-error=implicit-function-declaration` |
   | 14+ | `-Werror=incompatible-pointer-types` | 型不一致ポインタ代入がエラー | `-Wno-error=incompatible-pointer-types` |

2. **段階的対応戦略**: まず回避フラグで全体をビルド可能にし、その後個別に正しい修正を行う。
3. 回避フラグはプラットフォーム設定に集約し、将来的に除去する計画を立てる。

### アンチパターン
- ❌ 個々のファイルで `-fcommon` を付ける（設定が分散する）
- ❌ 回避フラグを入れずに1000+箇所の修正を先にやろうとする（ビルド不能期間が長くなる）

## DP-3: LP64 ポインタキャスト修正の定型パターン

### 目的
ILP32→LP64移行時の「ポインタ↔整数」キャスト警告を効率的かつ安全に修正する。

### ルール
1. 典型的なパターンと修正方法:

   | パターン | 元コード | 修正 |
   |---------|---------|------|
   | XtPointer→int (callback client_data) | `(int) client_data` | `(intptr_t) client_data` |
   | int→pointer (callback registration) | `(XtPointer) 42` | `(XtPointer)(intptr_t) 42` |
   | NULL→int型変数 | `xrm_name[2] = NULL` | `xrm_name[2] = 0` |
   | NULL→char型変数 | `*ptr = NULL` | `*ptr = '\0'` |
   | Window/Atom→int (X11) | `(int) window` | そのまま（X11のWindow/Atomは32bit） |

2. `#include <stdint.h>` を追加して `intptr_t` / `uintptr_t` を使用する。
3. X11の `Window`, `Atom`, `Colormap` 等は64bit環境でも内部的に32bitIDのためキャスト不要な場合がある。ただし `long` 型で受ける X API (XGetWindowProperty等) には注意。
4. 一括置換は `sed` で可能だが、`(int) client_data` のうち「本当にint値を渡している」ケース（enum値等）を誤変換しないよう注意。

### チェック方法
```bash
# LP64警告の検出
gcc -Wpointer-to-int-cast -Wint-to-pointer-cast -c file.c
# 修正後の確認
gcc -Wpointer-to-int-cast -Wint-to-pointer-cast -Werror -c file.c
```

### アンチパターン
- ❌ 全箇所を `(long)` にキャストする（LP64では動くがWindowsのLLP64で壊れる）
- ❌ 警告を `-w` で消して「解決」とする
- ❌ X11の32bit ID型（Window等）まで intptr_t に変更する（不要な変更）

## DP-4: POSIX TZ 文字列を glibc 互換に構築する

### 目的
旧 Unix 由来の `sprintf("TZ=%s%d%s", tzname[0], tz_off, tzname[1])` 形式 TZ 構築コードが、glibc で意図せず米国東部の DST 規則（範囲外では EST/EDT のオフセット）を適用して 2038年付近の日付計算をずらすのを防ぐ。

### ルール
1. POSIX TZ format で **DST 名指定あり、ルール省略**（例: `TZ=UTC0UTC`）は、glibc では既定規則ファイル `posixrules`（通常は America/New_York）の DST 切替日が使われる。遷移表の範囲内では指定オフセット（UTC、夏時間は UTC+1）で切り替わるが、**遷移表の最後より後の時刻ではファイル末尾の TZ 文字列（EST5EDT 相当）のオフセットがそのまま使われ、ゾーン名だけが UTC になる**。`posixrules` が無い場合は米国の既定規則（M3.2.0,M11.1.0）で夏時間期間に1時間ずれる。安全な形式は以下:

   | TZ 値 | 解釈 |
   |-------|------|
   | (unset) | `/etc/localtime` を使用（推奨） |
   | `UTC` | UTC 固定 ✅ |
   | `UTC0` | UTC、DST なし ✅ |
   | **`UTC0UTC`** | DST 名指定・ルール省略 → **米国東部の DST 規則を適用** ❌ |
   | `EST5EDT,M3.2.0,M11.1.0` | EST/EDT、明示ルール ✅ |

2. `daylight == 0` のときは DST 名（`tzname[1]`）を出力 TZ に含めない。
3. 可能なら `putenv("TZ=...")` を行わず、`tzset()` だけ呼んでシステム既定（`/etc/localtime`）に任せる。
4. 既存の `sprintf` パターンを残す場合は条件分岐する:
   ```c
   if (daylight) {
       sprintf(tzptr, "TZ=%s%ld%s", tzname[0], (long)offset_hr, tzname[1]);
   } else {
       sprintf(tzptr, "TZ=%s%ld", tzname[0], (long)offset_hr);
   }
   ```

### チェック方法
```c
unsetenv("TZ"); tzset();
printf("tzname=%s/%s daylight=%d\n", tzname[0], tzname[1], daylight);
/* daylight==0 なら DST 名を出力 TZ に含めないことを確認 */

/* 2038境界での差分を観測 */
setenv("TZ", "UTC0UTC", 1); tzset();
time_t t = 2147126400;          /* 2038/01/15 00:00:00 UTC */
struct tm *tm = localtime(&t);
/* ローカルが UTC のままか、EST/EDT のオフセットにずれるかを確認 */
```

### アンチパターン
- ❌ `tzname[0]`, `tzname[1]`, `timezone` を無条件に連結して TZ 文字列にする
- ❌ Solaris で動いた TZ 構築コードを glibc 環境にそのまま持ち込む
- ❌ DST のない UTC 環境で DST 名を含めた TZ を putenv する

### 実例
時刻表示ユーティリティの初期化処理で `TZ=UTC0UTC` が putenv された結果、日付検索機能の 2038年以降の日付表示が 1 日前にずれていた。`daylight` で分岐する修正で解消。

## DP-5: time_t を扱う関数の戻り値型を `time_t` に揃える

### 目的
LP64 で `time_t = long`（64bit）なのに、関数の戻り値型が `int`（32bit）で宣言されているコードを検出・修正し、2038年付近の暗黙的な切り詰めを防ぐ。

### ルール
1. `time_t`（または `time_t` の typedef = `Tick` 等）を受け取って時刻を返す関数の宣言は、戻り値も `time_t` に揃える。
2. 戻り値型が `int` のままだと、`time_t` 値（2038年以降は 32bit signed 範囲外）を返す際に暗黙の切り詰めで負数化する。コンパイラ警告が出ない経路がある（`int` → `time_t` への代入は警告されない）。
3. 修正時は **宣言（.h）と実装（.c）の両方** を変更する。

### チェック方法
```bash
# time_t / Tick を引数に取りながら戻り値が int の関数を検出
grep -rn '^extern int .*\(Tick\|time_t\)\|^int .*\(Tick\|time_t\)' .

# 値域での確認（境界年で挙動差分を観測）
# 関数を 2037 / 2038 / 2039 / 2040 / 2050 で呼んで戻り値を比較
```

### アンチパターン
- ❌ 戻り値型が `int` の時刻関数を「LP64 でも問題なさそうだから」放置する
- ❌ 呼び出し側で `(time_t)` キャストを足して解決した気になる（戻り値段階で既に切り詰め済）
- ❌ 警告が出ないことを根拠に修正不要と判定する

### 実例
DST（サマータイム）補正を行うユーティリティ関数の戻り値型が `int` だった。内部の日数計算関数で 2039年の時刻（> 2,147,483,647）を渡すと負数に切り詰められ、後続の範囲検索処理が破綻。戻り値型を `time_t`（相当のtypedef）に変更（実装・宣言とも）して解消。

## DP-6: Y2038 検証はレイヤー別に網羅する

### 目的
time_t の 64bit 化修正が API レイヤーだけでなく、アプリケーションのクライアント表示層・範囲計算層にも波及する問題を検出する。

### ルール
1. Y2038 修正後の検証は以下の全レイヤーで実施する:
   - (a) API: time_t を受け渡す関数インターフェース
   - (b) シリアライズ: XDR / RPC / ファイル I/O での time_t 表現
   - (c) ファイル永続化: DB / カレンダーファイルでの時刻保存形式
   - (d) クライアント表示: UI / CLI が時刻を表示する際の変換処理
   - (e) 範囲計算: 時刻の加減算・比較を行うユーティリティ関数

2. 境界年で挙動差分をスキャンする:
   - テスト対象年: 2026 / 2030 / 2037 / **2038** / **2039** / 2040 / 2050
   - 2038-01-19 03:14:07 UTC が signed 32bit の上限
   - 2038-01-19 03:14:08 UTC 以降は time_t が 2,147,483,647 を超える

3. **表示と取得の両方**を検証する:
   - 表示が正しくても、取得（検索・フィルタリング）が失敗する可能性がある
   - insert → lookup の往復テストを含める

### チェック方法
```bash
# 境界年テスト: 各年でデータ作成→取得→表示の一貫性を確認
for year in 2026 2030 2037 2038 2039 2040 2050; do
    # insert test data for $year
    # lookup and verify display matches
done
```

### アンチパターン
- ❌ API レイヤーの time_t 修正だけで「Y2038 対応完了」と宣言する
- ❌ 2038年のテストだけ行い、2039年以降を確認しない（2038年でも上限を超えるのは 1月19日 03:14:08 UTC 以降のため、年初などの日付では切り詰めが顕在化しない）
- ❌ 表示テストだけ行い、検索・範囲計算を確認しない

### 実例
カレンダー系APIの time_t を 64bit 化したが、クライアント側の時刻処理ユーティリティに 2 件の追加バグが残存:
- TZ構築処理: `TZ=UTC0UTC` が glibc で米国東部の DST 規則適用 → 2038年付近で日付ずれ (→ DP-4)
- DST補正関数の戻り値型 int: 2039年以降の値が負数に切り詰め → 範囲検索破綻 (→ DP-5)
いずれもデータ登録→検索のエンドツーエンドテストで初めて検出された。

## DP-7: ILP32→LP64 移行時の構造体レイアウト変化を検証する

### 目的
32bit (ILP32) から 64bit (LP64) への移行で `time_t`, `long`, ポインタのサイズが変わり、構造体のメモリレイアウト（サイズ・アラインメント・パディング）が変化する。これにより、バイト列を直接操作するコードが破綻するのを防ぐ。

### 要点
- ILP32 では `time_t`/`long`/ポインタが 4 バイト、LP64 では 8 バイトになり、
  構造体の sizeof・フィールドオフセット・配列の stride が変わる
- **フィールド名でアクセスしている限り安全**（コンパイラが正しいオフセットを計算する）
- 危険なのは「バイト列として扱う経路」: ファイルI/Oでの構造体一括 read/write、
  ハードコードオフセットによるポインタ算術、XDR/RPC での構造体丸ごとシリアライズ、
  32bit/64bit プロセス混在の共有メモリ、`n * sizeof` による memcpy
- 「リコンパイルしたから問題ない」は**永続化データとネットワーク通信には当てはまらない**

レイアウト変化の具体例、危険パターンの一覧、XDR での互換対応実装（`xdr_time_t_compat()`）は
**`docs/reference/ilp32-to-lp64-struct-layout.md`** を参照。

### チェック方法

```bash
# 構造体をバイト列として read/write している箇所を検出
grep -rn 'fread.*sizeof.*struct\|fwrite.*sizeof.*struct' .
grep -rn 'read(.*sizeof\|write(.*sizeof' . | grep struct

# ハードコードオフセットによるポインタ算術を検出
grep -rn '(char\s*\*)\s*.*+\s*[0-9]' . | grep -v '/\*'

# time_t/long を含む構造体でサイズ前提のコードを検出
grep -rn 'sizeof.*time_t\|sizeof.*long' . | grep -v 'malloc\|alloc'
```

### アンチパターン
- ❌ 「リコンパイルしたから問題ない」と判断し、ファイル永続化・ネットワーク通信を確認しない
- ❌ `sizeof(struct)` の変化を意識せず、既存データファイルの読み込みコードをそのまま使う
- ❌ コンパイラ警告が出ないことを根拠に問題なしと判定する（`char*` 経由のキャストは警告されない）

### 実例
カレンダー系APIのRPC通信で `time_t` がワイヤーフォーマットに含まれていた。
「ワイヤー上は 32bit 維持、メモリ上は 64bit」の方針を決定し、`xdr_time_t_compat()` で対応。
構造体フィールドアクセスは全てフィールド名経由だったため、レイアウト変化による実害は発生しなかった。

## DP-8: プラットフォーム config.h の作成ルール

### 目的
コピー元OSのconfig.hから新OS用を作る際に、「コンパイルは通るが実行時に壊れる」マクロ値の持ち越しを防ぐ。

### ルール
1. 各機能マクロ（`*_HAVE_*` / `*_USE_*` 等）について、新OS上での正しい値を `man` / 公式ドキュメントで**個別に**裏取りする。コピー元OSの値をそのまま流用しない。
2. 特に以下のカテゴリはOS間でセマンティクスが異なる可能性が高い:
   - accept継承 (O_NONBLOCK / INHERITED_NONBLOCK)
   - sendfile 引数・戻り値の違い
   - イベント機構の動作モデル（エッジ/レベル、再登録の有無）
   - atomic操作の戻り値・メモリオーダー
   - ソケットオプション名の違い (`TCP_CORK` vs `TCP_NOPUSH`)
3. ビルドが通ることは正しさの保証にならない。マクロ値の誤りは実行時まで検出できない。

### チェック方法
```bash
# config.h のマクロ一覧を抽出
grep '#define.*HAVE_\|#define.*USE_' src/os/unix/<newos>_config.h
# 各マクロについて:
man 2 <related_syscall>
# または公式ドキュメントで値を確認
```

### アンチパターン
- ❌ コピー元OSのconfig.hをそのまま使い、ヘッダだけ追加する
- ❌ 「ビルドが通ったからマクロ値は正しい」と判断する
- ❌ configureスクリプトが検出した結果を確認せずに信用する

## DP-9: 単体テストでは検出できないバグは初期化シーケンスを疑う

### 目的
「ミニマルテストでは正しく動くが、実バイナリ経由では誤動作する」状況で、原因を関数ロジックでなく `main()` 初期化の副作用に絞り込む。

### ルール
1. 単体テスト（関数の直接呼び出し）が正常で、実バイナリで再現する症状を観測したら、まず以下を疑う:
   - `main()` 冒頭で呼ばれるグローバル初期化関数（`init_xxx`, `setup_xxx`）
   - C++ static constructor
   - 環境変数の書き換え（`putenv`, `setenv`）
   - ロケール / タイムゾーン設定（`setlocale`, `tzset`）
   - シグナルハンドラ登録
2. 「初期化関数を呼ぶ版／呼ばない版」のテストを比較し、副作用を特定する。
3. 関数ロジックを修正しても症状が直らないなら、上記の初期化を再点検する。

### チェック方法
```c
/* 怪しい初期化関数を含む版と含まない版を作って差を観測 */
extern void init_xxx(void);   /* 怪しい初期化 */
int main(void) {
    init_xxx();               /* ← これを入れた版と入れない版で比較 */
    /* 同じ被疑関数を呼ぶ */
}
```
差が出たらその初期化関数が犯人。

### アンチパターン
- ❌ 単体テストが通った関数を「正しい」と確定し、別の箇所だけ調査する
- ❌ 再現条件を整える前に推測でパッチを当てる
- ❌ デバッグ出力を埋め込んだままコミットする

### 実例
日付ルックアップ機能が2038年で前日を表示するバグ。表示処理の関数を直接呼んでも再現せず、ミニマルテストでは全年正常動作。`main` 経由でのみ再現し、原因は初期化関数内の `putenv("TZ=UTC0UTC")` が glibc で米国東部の DST 規則付きとして解釈され、2038年の日付に EST/EDT のオフセットが適用されていた（→ DP-4）。
