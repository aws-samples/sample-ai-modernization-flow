# Method — 移行フロー（Phase 0-4）

移行・モダナイゼーションの型（Methodology）。ドメイン・ツールに依存しない。
ドメイン固有の観点は各 Playbook（`../playbooks/<domain>/`）が、AI実行規律は Harness
（`../harness/`）が提供する。

## フロー概要

各Phase境界の通過はTier 2（同期ゲート）であり、Phase完了条件との突合・暗黙判断の掘り起こし・
ADR実績レビュー・ナレッジ棚卸しを行う（harness コア規律「HOLD-8」＝Tier 2・停止確認ゾーン）。

**独立検証（skills/migration-adversarial-review）は「移行完了宣言」と「HOLD-1 の機能除外」に限り、
実施は1回である**（findings は移行対応台帳に起票して処理区分で閉じる。レンズの再掃引はしない）。
それ以外の境界では**検出器の否定テスト**（CP-13）が同じ役目を機械的に、かつ再実行可能な形で果たす。
とくに **work-plan の確定（Phase 2→3）には適用しない** — work-plan の行は Phase 3 で追加・変更できるため
不可逆ではなく、計画の誤りは Phase 3 のビルドと golden-path E2E がより高い精度で暴く。
可逆な境界で残った findings は移行対応台帳に `未対応` 行として繰り越して前進する。

**開始に必要な情報は「対象ソースのルートパス」と「off-limits」だけ**である。現行スタックは
Phase 0a の分析が明らかにし、移行先スタックは Phase 0b で決める。それ以外のプロジェクト情報は
エージェントが起動インタビューで埋める（harness コア規律「起動インタビュー」）。

```
Phase 0a: アセスメント — コード分析の実行  ★ここで終了できる（停止点1）
  → リポジトリ棚卸し: 対象ルート配下の全リポジトリ/ビルドルートを列挙し
     repository-inventory.md に記録（.git の有無だけに頼らない）
  → **進め方の判定（最初に行う）**: 分析結果が既にあれば既存結果を使う。
     git準備・transform-config作成・ATX実行を丸ごとスキップする（0a-0）
  → 分析対象の確認（軽い停止点。既定は全件対象、削るなら利用者が指示）
  → リポジトリごとの git 準備: 未管理なら git init（許可された操作のみ）、
     管理下なら実行前のブランチ名と HEAD を記録
  → transform-config 作成（リポジトリごと。4096バイト以内。テンプレートはPlaybookが提供）
  → ATX 分析実行: **AWS/comprehensive-codebase-analysis（構造・技術的負債）を
     リポジトリごとに1本**。リポジトリ間は並列
     ※ 並列の単位は git work tree。同一 work tree 内での並列実行は不可
     ※ 既存結果を使う場合はこのステップ自体を行わない（0a-2b）。分析時点のコミットが不明なのが
       既定であり、Phase 2 の裏取り（CP-3）で担保する。この確認で停止しない
  → 実行台帳 analysis-runs.md に来歴・終了コード・元ブランチ復帰確認を記録
  → 00-analysis/README.md（成果物の入口）を生成
  == Phaseゲート == 完了条件は `./verify.sh assessment` で機械確認する
     停止するかは migration-project.md の「アセスメントのみで終えるか」で決まる:
       yes（既定）→ 停止して確認。成果物は「分析結果そのもの」
       no        → 停止せず 0b へ直行（0a→0b の間に利用者の判断は無い）

Phase 0b: アセスメント結果の統合  ★ここで終了できる（停止点2）
  → リポジトリ横断の統合: システム全体構成図、横断の環境差異テーブル
     ※ **対象が1リポジトリなら構成図と契約棚卸しは N/A**（理由を台帳に記録して飛ばす）
  → ★ 移行対応の網羅の基準を確定: **Playbook の観点表（analysis-appendix.md）のうち
     対象に該当する観点**を選ぶ（CP-11）。**コードのパターン走査ヒット数を網羅の基準にしない**
     — ビルドが列挙する観点を先取りしても価値がなく、単位が混在して算術も成立しない
  → ★ リポジトリ間契約の棚卸し（API/イベント/共有DB/共有ファイル）
     — frontend/backend 境界は HOLD-2 の対象であり後戻りコストが最も高い
  → 技術的負債と移行先候補の整理（LTS・サポート状況・互換連鎖）
  → 概算の作業規模と主要リスク
  → ★ 移行方針の決定（ADR化。ユーザー承認必須）— **移行先スタックはここで決める**
  == Phaseゲート(Tier 2 = HOLD) == 成果物は「移行するかどうかの判断材料」
     ここで終了する場合: 移行に進むかの判断を利用者に返す

Phase 1: 準備
  → 依存ライブラリの changelog 調査（ドメイン固有の観点は analysis-appendix.md 参照）
  → ★ baseline取得のモード確定 + 実施(CP-5):
      モードA(旧環境で実測) = 旧環境が使えるなら実機観測で Characterization Test 化
      モードB(コード読解で定義) = 旧環境が無いならコードリーディングで期待動作定義
        （根拠・確度を併記）
      モードC(既存テストを流用) = 既存ユニット/E2Eテストをモダナイズして回す
        （テスト基盤自体の移行が作業スコープに入ることに注意）
  → ★ 非機能要件のスコープ判断（性能/リーク/障害耐性/セキュリティの対象・対象外をADR化。
      ユーザー承認必須）
  == Phaseゲート(Tier 2 = HOLD) ==

Phase 2: 分析・計画
  → ATX結果の実コード裏取り(CP-3)。**取り込んだ結果ほど裏取りの価値が高い**
  → 「ATX指摘 vs 実コード」対比表作成
  → コード変換はエージェントが直接修正で行う。ATX の Managed Transformation (MT) や
     Transformation Definition (TD) による変換は使わない。ATXの変換では個々の変更の判断が
     利用者に上がらず、ADRが残らないためである（ATXは Phase 0a の分析にだけ使う）
  → 段階的work-plan作成（最小構成→段階的機能追加）。複数リポジトリなら
     Stepの割り当てはリポジトリ単位になり、移行順序自体がADR相当の判断になる
  → ★ 観点ごとに**検出コマンドと否定テスト**を用意する（CP-11 / CP-13）。
     件数は Phase 3 で検出器を回して得る（計画段階で全量を数値化しない）
  → ★ work-plan確定と同時に、成功基準テーブルからスコープ内全成果物を
     verify.sh の期待リストへ登録する(CP-7)。未ビルドでも先に登録
  → ★ work-plan.md の `WORK-PLAN-STATUS` を CONFIRMED に書き換える
     — これで verify.sh の build/smoke/integration ゲートが本適用になる
  → 知見ドキュメント（Playbookの reference/ 配下）の反映
  == Phaseゲート(Tier 2 = HOLD) == work-plan承認
     ★ **独立検証は行わない。** work-plan の行は Phase 3 で追加・変更できるため不可逆ではない。
       確認するのは「観点表の該当観点を採用できているか」と「各観点に検出器と否定テストがあるか」
       の2点だけでよい。計画の妥当性そのものは Phase 3 のビルドと golden-path E2E が検証する

Phase 3: 実装・検証ループ（Tierゲート運用 — harness コア規律参照）
  → Step 1: setup-modernized.sh で実装ツリー(../<product>-modernized)を用意
            起点情報を session-context.md・work-plan.md に記録
            ★ Step 1 完了時に verify.sh の smoke ゲートを実装する
              （未実装のまま Step 2 以降に進むのは禁止）
  → work-plan の各Step順に実装する:
      Tier 0: plan内の作業は verify 全PASS 維持を条件に自律実行
      Tier 1: 記録・知見追記・コミット・Step間の移行は停止せず実行（人は後からバッチレビュー）
      Tier 2: 機械的トリガー（機能除外/ワイヤーフォーマット変更/仮説ログ3行/ADR相当判断等）
              で停止し、ADRドラフトを添えて人の判断を仰ぐ
  → ★ 観点の検出器を回して**その観点の全量**を得る → 直す → 再実行して0 → verify で固定（CP-11）
  → 各Stepで ./verify.sh 全8ゲート（build→smoke→integration [→nonfunc] →
     repo-sync→knowledge→adaptation→project）
     → コミット（コードは実装ツリー側、記録は記録リポジトリ側）
  → 成功基準テーブルとの突合(CP-6)
  → セッション終了時: 終了チェックリスト（両リポジトリの commit+push+整合確認）
  == Phaseゲート(Tier 2 = HOLD) ==

Phase 4: 最終確認
  → 全モジュール有効ビルド、全テスト実行、baseline差分確認
  → 移行対応台帳の突合: 未対応件数がゼロであること
  → ★ 全観点の検出器を再実行し、否定テストの記録を残す（CP-13）
  → ★ 移行完了宣言の独立検証（skills/migration-adversarial-review）— 生成者の自己申告で
     確定しない。2レンズ（機能欠落/スコープ）で反証を試み、観点表の網羅性を確認して記録する
     （独立検証と否定テストの記録がないと ./verify.sh adaptation が FAIL する）
  → ★ **独立検証は1回。** findings は台帳に起票して処理区分を与えて閉じ、`./verify.sh` を
     再実行して全PASSを確認する。**レンズの再掃引はしない**（機械で回る検査に変換して固定する）
  → ★ 踏んだ新しい観点を Playbook の観点表へ戻す（CP-11。案件で終わらせない）
  → 追加作業があれば「サブタスク開始: <taskname>」で実施
```

**Phase 4後の後続タスク（本フローのスコープ外・参照のみ）:**
デプロイ環境の設計・構築（アーキテクチャ設計 → 自動レビュー → IaC実装）は実際の移行では
必ず発生するタスクである。ターゲット環境の制約がアプリ改修に逆流することもある
（実例: マルチインスタンス構成のためのローカルファイルベース検索エンジン→マネージド検索への移行）。
現時点では本フローに含めず、AI駆動開発プロセスのインフラガードレール整備
（予防的統制・検知的統制）と合わせて別途計画する。

注: 完了基準は常に「文書の承認」ではなく「テスト・観測結果という証拠」に置く。
注: 単一リポジトリは「N=1 の特殊ケース」として同じ手順を通る（棚卸しは1行、並列は発生しない）。

## Phase 構成について（設計註）

フローを短くしようとすると必ず出てくる2つの提案がある。どちらも検討して採らなかった。

**Phase 0 を Phase 1 に統合する。** 採らない。Phase 0 と Phase 1 では**利用者に求める判断の重さが違う**。
Phase 0 は「やるかどうか」を決める材料を作る段階で、ここで止まること自体が正当な結果である（アセスメント
のみの利用）。Phase 1 は「やる」と決めた後に方法を決める段階で、ここで止まるのは失敗である。統合すると
**この境界が消え、アセスメントで止まった案件が「未完了」に見える**。

また Phase 境界には HOLD-8（Phase ゲート定型確認）が一様に効いている。統合すると Phase 0a の分析結果と
Phase 0b の移行方針という**性質の違う2つの成果物が1つのゲートで確認される**ことになり、確認が形骸化する。

**Phase 1 が薄いので Phase 2 に統合する。** 採らない。Phase 1 が薄いのは**意図的**である。ここは作業を
する段階ではなく、Phase 0 の分析結果を受けて work-plan を確定させる**決定のためのゲート**である。薄さは
機能であって欠陥ではない。統合すると、計画の確定と実装の着手が同じ Phase に入り、
`WORK-PLAN-STATUS: CONFIRMED` を打つ瞬間が曖昧になる（検証ゲートの適用がこのマーカーで切り替わるため、
曖昧になると初日の期待リスト登録が形骸化する）。

**Phase 番号を振り直さない。** Phase 番号は文書全体の共有アンカーであり、`Phase` は日英で翻訳しない語
として固定されている。振り直しは広範囲に波及する。

## 3つの終了点

本フローは3通りの使い方が同じ導線で成立するように設計されている。

| 終了点 | 成果物 | 用途 |
|--------|--------|------|
| **Phase 0a 完了** | ATX分析結果（HTML化済み）、リポジトリ棚卸し、実行台帳 | 分析結果そのものが欲しい。他チームへの引き渡し、社内レビュー |
| **Phase 0b 完了** | 横断統合、移行先候補、概算規模とリスク、移行方針ADRドラフト | 移行するかどうかを判断したい |
| **Phase 4 完了** | 移行済みの実装ツリーと検証記録 | 移行を完遂する |

Phase 0a/0b で終了する場合も `install.sh` の実行内容は同じである（モードを分けない）。
work-plan が未確定のうちは verify.sh の build/smoke/integration ゲートが「未適用」となり、
Phase 2 で CONFIRMED にした時点で本適用に切り替わる。

## 利用者が明示的に判断すべき項目

以下は**フローが自動では決めない・利用者の明示判断が必要**な項目。プロジェクト開始時に目を通し、
該当する判断を「暗黙のまま」にしないこと。多くはADRとして記録される（=Tier 2で承認を求められる）。

| # | 判断項目 | いつ | 判断しないとどうなるか |
|---|---------|------|---------------------|
| 1 | **分析対象リポジトリの確定**（対象/対象外とその理由） | Phase 0a | 分析コストがリポジトリ数に比例して膨らむ。「対象外」が暗黙化して後で漂流する |
| 2 | **移行方針**（移行先スタック、除外する機能の方針） | Phase 0b | 分析結果を見る前に決めると前提を誤る。決めないと Phase 2 の計画が立たない |
| 3 | **baselineのモード選択**（A=旧環境で実測 / B=コード読解で定義 / C=既存テストを流用） | Phase 1 | 旧環境が消えてからでは実測不能。モードB（コード読解で定義）の確度リスクが不可視になる |
| 4 | **非機能要件のスコープ**（性能/リーク/障害耐性/セキュリティの対象・対象外） | Phase 1 | 「対象外」が暗黙化し、実装終盤で残ゲートとして漂流する（メモリリーク検証ツールの適用範囲が実装終盤まで未確定だった実例あり） |
| 5 | **複数リポジトリの移行順序**（backend先行か同時か） | Phase 2 | リポジトリ間契約の互換期間が設計されず、途中で結合できなくなる |
| 6 | **長時間試験の実施計画**（1時間規模の稼働試験等、実行主体と実施タイミング） | Phase 1-2 | 実行主体が決まらず先送りされ続ける |
| 7 | **Tier 2トリガーの調整**（多発時の基準緩和、ADR実績レビューによるTier降格） | Phaseゲート | ゲートが形骸化 or 過剰化する。緩和は実績データに基づき明示的に行う |
| 8 | **ナレッジ棚卸し**（practices/LLの統合・削除） | Phaseゲート/振り返り | 知見ファイルが肥大化しノイズ化する |
| 9 | **クラウドリソースをAIが操作する場合のガードレール**（IAM境界・Policy as Code） | 該当時 | 本フレームワークは単一ホスト内作業を前提としており、クラウド操作の統制は**未提供**。必要なら別途整備 |
| 10 | **本番相当データのテスト利用可否**（マスキング・匿名化ルール） | 該当時 | コンプライアンスリスク。ルール策定は常に人の判断（Tier 2）に残す |

## 設計原則

1. **Single Source of Truth**: 行動規律は harness、ドメイン知見は Playbook（practices.md）に集約
2. **Constraints > Prompts**: ルールは `./verify.sh` で仕組みとして強制する。プロンプトだけでの制約は信頼しない
3. **Tierガバナンス**: 人の判断は後戻りコストの高い決定と理解形成の節目に集中させる。エスカレーション条件は機械的な基準で定義する（harness コア規律）
4. **完了基準は証拠**: 各Phase/Stepの完了は「文書の承認」ではなく「テスト・観測結果の蓄積」で判定する
5. **AI出力は仮説**: AI分析結果は必ず実コードで裏取りする（CP-3）。プロジェクト設定の推定値も同じ扱いとし、出所を区別する
6. **ビルド成功 ≠ 完了**: 実行時テストで観測するまで未完了（CP-4）
7. **検証ゲート = 成功基準テーブル**: 全基準を自動テストに含める（CP-6）。スコープ内全成果物を初日に登録する（CP-7）
8. **知見は蓄積する**: 共通知見は `practices-common.md`、ドメイン知見は `practices.md`、固有教訓は `lessons-learned.md` に分離蓄積。採用案だけでなく棄却した選択肢と理由も記録する
9. **ツールチェーンが列挙できるものを事前に数えない**: 事前に持つのは「ビルドが**沈黙する**／**誤誘導する**観点」であり、コードの走査ヒット数ではない。観点は移行経路ごとの資産として Playbook（`analysis-appendix.md`）で案件をまたいで育てる（CP-11）
10. **観点は検出コマンドを携帯する**: 説明文だけの観点は全量が出ない。検出器には**否定テスト**を付け、「その検出器が本当に検出できる」ことを機械的に示す（CP-13）。完了宣言と機能除外以外の境界では、これが独立検証の代わりになる
