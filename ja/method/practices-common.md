# 移行プラクティス集 — 共通 (Common Practices)

移行・モダナイゼーションプロジェクト全般（ドメイン・言語を問わない）に適用する共通プラクティスを
`CP-N` 形式で蓄積する。ドメイン固有のプラクティスは各 Playbook の `practices.md` に `DP-N` 形式で記載する。

---

## このドキュメントについて

### 目的
- 全ドメイン共通の移行プラクティスを `CP-N` 形式で蓄積する（本ファイルは method 層に属する）。

### 読み方（AIエージェント向け・重要）

**エージェントが既定で読むのは「サマリ」表だけである。** 本文は該当するテーマに当たったときだけ開く。
本文には実例・アンチパターン・コード例を詳しく書いてよい（**本文は人が読んで理解するための層**であり、
短くすることが目的ではない）。この2層構造がコンテキスト負荷と説明力の両立の仕組みである。

同じく **`worklog.md` は時系列で読まない。** 前回状態の把握は `session-context.md` から行う
（worklog は追記専用で肥大するため）。

### 採番ルール

1. **共通プラクティスは `CP-N` 形式・本ファイルで一元管理する連番**を使う（次の空き番号を使う）。
2. **ドメイン固有プラクティスは各 Playbook の practices.md で `DP-N` 形式・そのPlaybook内で一元管理する連番**を使う。
   `CP-N` と `DP-N` はプレフィックスが異なるため番号空間は独立している（重複を気にする必要はない）。
3. **`DP-N` は Playbook をまたいで重複してよい**（例: clang PlaybookのDP-3とjava PlaybookのDP-3は無関係）。
   1プロジェクトには共通+1つのPlaybookしか入らないため、実行時に重複が問題になることはない。
   Playbook間で言及する場合は「〈domain名〉PlaybookのDP-N」のように所属を明示する。

#### 採番の権限（フレームワークとプロジェクトの分離）

**無印の `CP-N` / `DP-N` を採番できるのはフレームワーク本体だけである。**
プロジェクトにコピーされた `docs/knowledge/` 配下の知見ファイルは**参照＋プロジェクト名前空間での追記用**であり、
無印の次番を勝手に使ってはならない。

| 採番する主体 | 使う形式 | 例 |
|------------|---------|-----|
| フレームワーク本体 | `CP-N` / `DP-N`（無印） | `CP-13`, `DP-10` |
| 個別プロジェクト | `CP-<project>-N` / `DP-<project>-N` | `DP-myapp-1` |

プロジェクト側の知見は完了時にフレームワーク本体へ還元し、そこで無印の番号を与える。
**欠番は保持し、再利用しない。**

> これは実際の事故への対策である。稼働中のプロジェクトが独自に `DP-5` を採番し、
> Playbook 本体の `DP-5` と**別内容で衝突**した実例がある。
> 「測ってから採る」方式は測定と採番の間に隙間がある限り破れるため、名前空間で構造的に分離する。

### 追記ルール

1. 新エントリは本ファイル末尾の `ENTRIES END` マーカー（本ファイル末尾の HTML コメント1行）の**直前**に挿入する（このマーカーは移動しない）。
2. 各エントリは `## CP-N: <タイトル>` 形式で、以下の節構成に揃える:
   - `### 目的` / `### ルール` / `### チェック方法` / `### アンチパターン` / 任意で `### 実例（プロジェクト名）`
3. 「サマリ」表に新エントリの行を追加する。
4. プロジェクト内で得た汎用知見はプロジェクトの `docs/knowledge/practices-common.md` に
   **プロジェクト名前空間で**追記し、プロジェクト完了時に本ファイルへ還元する。

### 量の規律（`./verify.sh knowledge` が機械検査する）

散文のルールは自己申告で素通りするため、量は数値で縛り、ゲートで検査する。
既定値は実測に基づく（本ファイルと2つの Playbook の実測分布は本文 29〜72行、サマリ行 175〜215バイト）。

| 対象 | 既定の上限 | 超えたときの対応 |
|------|-----------|----------------|
| サマリ1行 | 300 バイト | 一言に収まらないなら、それは本文に書くべき内容 |
| 1エントリの本文 | 80 行 | 詳細を `docs/reference/` へ分離し、本文には要点とポインタを残す |
| 1ファイルのエントリ数 | 15 件 | 統合・削除を検討する（下記） |

- 上限はプロジェクト側の `verify.sh` で調整できる（`KNOWLEDGE_MAX_*`）
- **行数上限は言語中立ではない**（同一内容で英語は日本語の約1.4倍の行数になる）。
  既定値は英語側の実測に余裕を持たせた値である
- **エントリ数の超過は「統合を強制する」トリガー**である。統合しない判断をする場合は、
  ファイル冒頭に理由を記録する:
  `<!-- KNOWLEDGE-REVIEWED: YYYY-MM-DD (N entries, consolidation deferred: <理由>) -->`
  記録があればゲートは通る（**記録なき超過だけを弾く**）。
  Phaseゲート/振り返りでの棚卸しが「提案だけで実行されない」状態を防ぐための設計である

### 網羅の基準の語彙（「分母」と呼ばない）

網羅性を数値で担保する仕組みを指すとき、次の語を使う。読み手に用語の学習を強いないため、
既存語彙を優先し、**「分母」という表現は使わない**。

| 対象 | 用語 | 実体 |
|------|------|------|
| 成果物（実行ファイル・ライブラリ・war/jar等） | **期待リスト** | `verify.sh` の `EXPECTED_ARTIFACTS`（CP-7） |
| 移行に伴い手を入れる箇所 | **移行対応台帳** | `01-plan/adaptation-ledger.md`（処理区分つき。数えるのは該当する観点 = CP-11） |
| 概念として語るとき | **網羅の基準** | 「何件あるかを機械的に数えられる独立した一覧」 |
| 統計的な無作為抽出を行う場面 | **母集団** | 統計の標準用語。本フローで無作為抽出は行わないため、原則として登場しない |

台帳のうち手を付けずに残った件数を **未対応件数** と呼び、これをゼロにすることを指標とする。

## サマリ

| ID | タイトル | 一言 |
|----|---------|------|
| CP-1 | 依存ライブラリの振る舞い変更調査 | API互換 ≠ 動作互換。CHANGES/NEWS で事前検出 |
| CP-2 | 調査プロセスのルール | 最終成功まで再検証。真因を1つに早期断定しない |
| CP-3 | AI分析結果の取り扱い | AI出力は仮説。実コードで裏取りしてから計画に含める |
| CP-4 | コード修正の完了条件 | ビルド成功 ≠ 完了。観測テストで確認するまで未完了 |
| CP-5 | Baseline Behavior Tests | 移行前に旧動作を記録し、移行後に差分検出する |
| CP-6 | 検証ゲートと成功基準テーブルの完全一致 | 自動テストに全基準を含める。手動チェックに頼らない |
| CP-7 | スコープ内全バイナリを検証ゲートに初日登録する | 未登録は「存在しない」のと同じ。FAIL でも可視化する |
| CP-8 | 根本原因は因果の実証をもって確定する（仮説ログ） | ON/OFFで症状が再現/消失するまで「仮説」。試行ごとに仮説ログ1行 |
| CP-9 | 公式マイグレーションガイドを変換計画前に網羅確認する | 多段メジャージャンプはガイドも複数。破壊的変更を計画に転記しURLを参照記録 |
| CP-10 | 移行先スタックの事前検証（EOL/互換マトリクス/PoC） | 変換開始前に移行先の組み合わせを検証。互換の矛盾は後工程で大きな手戻りになる |
| CP-11 | 移行対応台帳は「観点」を網羅の基準にし、件数は作業中に検出器で得る | ツールチェーンが列挙する観点を事前に数えない。観点は検出コマンドを携帯する。網羅の基準は移行経路ごとの資産 |
| CP-12 | 検証ツールはホスト環境に問い合わせない形で書く | 実在判定を FS に委ねず一次情報と厳密比較する。GNU専用オプション禁止。件数が出ていることは正しさの根拠にならない |
| CP-13 | 検出器には否定テストを付ける | 「0件」は「無い」とも「検出できていない」とも読める。壊して EXIT≠0 を確認するまで検出能力は未証明 |

## CP-1: 依存ライブラリのメジャーバージョン差がある場合の事前調査

### 目的
APIが残っていても振る舞い（セマンティクス）が変わったケースを、動作確認で詰まる前に発見する。

### ルール
1. 移行元→移行先でメジャーバージョンが変わるライブラリを特定する。
2. 各ライブラリのCHANGES/NEWS（全メジャー版境界分）を一次ソースとして読む:
   - **新設された互換オプション・フラグを列挙し、各々「なぜ追加されたか」を確認する**
     → 新設オプション = 「旧動作に戻すスイッチ」 = 「壊れた振る舞いがある」のシグナル
   - **デフォルト値が変わった項目を最優先で洗い出す**
3. 上記各項目について、本コードベースのどの箇所が影響を受けるか特定する。
4. 可能なら旧環境が生きているうちに「両版の差分テスト」を作る。

### チェック方法
```bash
# 検索クエリは「現象」で投げる:
# ✅ "OpenSSL 3.0 SSL_read returns 0 behavior change"
# ❌ "OpenSSL 3.0 migration guide"（振る舞い変更は薄い）
```

### 報告形式
| ライブラリ | 変更内容 | 旧動作 | 新動作 | 互換オプション | 影響箇所 |
|-----------|---------|--------|--------|--------------|---------|
| (例) OpenSSL 3.x | unexpected EOF handling | SSL_ERROR_WANT_READ | SSL_ERROR_SSL | SSL_OP_IGNORE_UNEXPECTED_EOF | ssl_recv() |

### 振る舞い変更の検出難易度

| 種類 | 検出のしやすさ |
|------|--------------|
| API削除・シグネチャ変更 | コンパイル/リンクで自動検出 |
| **振る舞いの変更** | コンパイル成功・部分動作。特定状態でのみ顕在化 |

### アンチパターン
- ❌ 依存ライブラリは「ビルドが通れば互換」と判断する
- ❌ migration guideだけ読んで「振る舞い変更なし」と結論する
- ❌ 旧環境が廃止されてからテストを書こうとする

## CP-2: 調査プロセスのルール

### 目的
問題発生時に効率的に根本原因に到達する。

### ルール
1. **「変えていないコードは正しい」を起点にする。** git差分で触ったファイルと触っていないファイルを分け、後者で問題が出たら環境の振る舞い差を第一容疑にする。
2. **1つ修正したら最終成功まで再検証する。** 途中指標（エラーコードの変化等）で「解決した」と判断しない。
3. **症状の性質が変わったら観測手段を変える:**
   - エラー → debugログ + ライブラリエラーキュー
   - 遅延/ハング → `strace -T`（syscall所要時間）
   - イベント問題 → debugログのイベント登録/削除
4. **syscall層・ライブラリ層・アプリ層の3点を同時に見る。**
5. **もっともらしい仮説ほど一次証拠で早期に殺す。**
6. **「真の原因が1つ」と早期断定しない。** 修正後も症状が残るなら別のバグが奥にある。

### チェック方法
```bash
# 変更ファイルの一覧
git diff --name-only HEAD~N
# syscall層の観測
strace -T -e trace=network -p <pid>
# ライブラリエラーキュー
openssl errstr <error_code>
```

### アンチパターン
- ❌ 「修正したら症状が変わった」=「解決」と判断する
- ❌ 最も確からしい仮説を唯一の原因として追い、他の可能性を排除する
- ❌ エラーログだけを見てsyscall層を確認しない

## CP-3: AI分析結果の取り扱い

### 目的
AIツール（Amazon Q Transform / Kiro / Claude Code / Cursor / GitHub Copilot等）の分析結果を鵜呑みにせず、実コードとの突き合わせを確実にする。

### ルール
1. **AI分析結果は「一般的な指摘」であり、実際のコードの状態を保証しない。** コードベースの履歴やカスタマイズを反映していない可能性が常にある。
2. AI分析結果からwork-planに含める項目は、**必ず実際のソースコードをgrep/読み込みして確認してから**工数見積もりに反映する。
3. 確認結果を「AI指摘 vs 実際のコード状態」の対比表として出力する。
4. 実際に問題が確認された項目のみをwork-planに含める。

### 指示テンプレート（AIツール共通）
```
AI分析結果を出発点として、以下の手順で作業計画を作成してください:
1. 分析結果から「修正が必要そうな項目リスト」を抽出する
2. 各項目について、実際のソースコードをgrep/読み込みして確認する
3. 確認結果を「AI指摘 vs 実際のコード状態」の対比表として出力する
4. 実際に問題が確認された項目のみを作業計画に含める
5. 他のPBルールに従うこと
```

### アンチパターン
- ❌ 「AI分析結果をもとに作業計画を作って」（裏取り工程が抜ける）
- ❌ コピー元OSのconfig.hをそのまま使い、ヘッダだけ追加する
- ❌ 依存ライブラリは「ビルドが通れば互換」と判断する
- ❌ AI分析が「7-8箇所の修正が必要」と言ったらそのまま工数に反映する

## CP-4: コード修正の完了条件

### 目的
「修正した」と「正しく動作する」の間のギャップを防ぐ。

### ルール
1. コード修正の完了条件は「期待する出力がテストで確認できた」こと。ビルド成功は完了条件ではない。
2. 修正箇所ごとに「何を観測すれば正しいか」を**修正前に**定義する:

   | 修正の種類 | 観測方法 |
   |-----------|---------|
   | HTTPヘッダ値の変更 | `curl -I` でヘッダを確認 |
   | Cookie値の変更 | `curl -I` で Set-Cookie を確認 |
   | エラーメッセージの変更 | エラー条件を発生させてログ確認 |
   | 設定値デフォルトの変更 | 設定を省略した状態で動作確認 |
   | 数値定数の変更 | その定数が使われるパスを通して出力確認 |
   | SSL/TLS関連の変更 | `curl -v https://...` でハンドシェイク含め確認 |

3. 「前のセッションで完了済み」項目も、テスト結果の記録がなければ未検証として扱う。
4. 固定文字列の修正は特に注意: grepで確認しただけでは不十分。実際にレスポンスに含まれるパスを通るテストが必要。

### チェック方法
```bash
# 修正前に定義した観測コマンドを実行
# 例: curl -I https://localhost/ | grep "Set-Cookie"
# 結果を 02-test/test-results/ に保存
```

### アンチパターン
- ❌ ビルド成功をもって「修正完了」と記録する
- ❌ 修正と同じセッション内で検証せず、次回セッションに回す
- ❌ 条件分岐の片方のみ実行されるコードを、正常パスのテストだけで検証する

## CP-5: Baseline Behavior Tests（移行前動作記録）

### 目的
移行前に旧環境での「正常動作」を記録し、移行後に同じ出力が得られることを保証する。回帰を「差分」で検出できる仕組みを作る。

### ルール
1. **Phase 2（分析）完了後、Phase 3（実装）開始前**に旧環境で正常動作を記録する。
2. 旧環境が生きているうちにしか取得できないデータがある。最優先で実施すること。
3. 記録は `02-test/test-results/baseline/` に保存する。
4. 移行後に同じコマンドを実行し、baseline との差分を比較する。

### 取得すべき項目（アプリケーション種別に応じて選択）

| カテゴリ | 取得コマンド例 | 目的 |
|---------|--------------|------|
| HTTP応答 | `curl -v http://host/` 全文 | レスポンス形式・ヘッダの一致確認 |
| HTTPS応答 | `curl -v https://host/` 全文 | TLSハンドシェイク含む正常性 |
| Cookie/セッション | `curl -I http://host/path` | expires値等の形式確認 |
| エラーログ（正常時） | error.log コピー | debugログの正常パターン把握 |
| syscallトレース | `strace -e trace=network -p <pid>` 1リクエスト分 | 正常時のsyscall列パターン |
| 設定デフォルト | 設定ファイルなしで起動した出力 | デフォルト値の動作把握 |
| パフォーマンス | `time curl ...` / `ab` 等 | 性能劣化の検出用ベースライン |

### チェック方法
```bash
# 移行後の比較
diff 02-test/test-results/baseline/http-response.txt \
     02-test/test-results/phase3/http-response.txt
```

### アンチパターン
- ❌ 旧環境が廃止されてからテストケースを考え始める
- ❌ 「正常動作は知っているから記録不要」と省略する
- ❌ baseline記録なしに「移行前と同じ動作のはず」と宣言する

## CP-6: 検証ゲートと成功基準テーブルの完全一致

### 目的
成功基準テーブルに定義した項目が検証ゲート（自動テスト）に含まれないことによる検証漏れを防ぐ。

### ルール
1. 成功基準テーブル（必須・推奨）の**全項目**を、実行可能な自動テストとして検証ゲートに含める。手動チェックリストに留めない。
2. 検証ゲートの実装時に、成功基準テーブルとの**双方向突合**を行う:
   - テーブルの各項目 → 対応するテストが存在するか
   - テストの各項目 → テーブルに根拠があるか
3. 検証ゲートのファイルは、ビルドシステムに上書きされない場所・名前にする（例: `verify.mk`, `scripts/verify.sh`, `ci/gate.mk`）。
4. Step完了宣言の前に「検証ゲートを実行し、全項目PASSを観測した」ことを記録に含める。

### チェック方法
```bash
# 成功基準テーブルの項目数
grep -c "^| M\|^| R" 01-plan/work-plan.md

# 検証ゲートのテストターゲット数
ls 02-test/integration/*.sh | wc -l   # 登録済み統合テスト数の確認例

# 両者の数が一致しているか確認
```

### アンチパターン
- ❌ 成功基準テーブルを定義したが、検証ゲートには一部しか実装しない
- ❌ 「make verify PASS = 全基準クリア」と短絡し、テーブルとの突合を省略する
- ❌ ビルドシステムが上書きするファイル（Makefile等）に検証ロジックを書く
- ❌ 推奨基準を「推奨だから省略可」としてテストから除外する

## CP-7: スコープ内全バイナリを検証ゲートに初日登録する

### ルール

- 作業計画でスコープ内と定義したビルド対象は、**ビルド可否にかかわらず**検証ゲート（verify.sh 等）に全数登録する
- ビルドが通らないものは FAIL として可視化し、スキップする場合は理由をコメントで明記する
- 「後で対応」の暗黙スキップを許容しない — スキップは明示的な判断として記録する
- 検証ゲートの項目数と work-plan のスコープ定義を定期的に突合する（CP-6 の具体化）

### なぜ必要か

移行作業は長期化しやすく、途中で注力先が移る。検証ゲートに登録されていないものは「存在しない」のと同じで、完了判定時まで漏れが検出されない。これはビルド対象、テスト対象、設定ファイルのいずれにも当てはまる。

### 適用タイミング

- work-plan 作成直後（Phase 1 完了時）
- スコープ変更のたびに検証ゲートの期待リストと突合

### アンチパターン

- 「ヘッダが足りなくてビルドが止まった → 後でやる」と口頭で決めて検証ゲートに登録しない
- 全項目 PASS のまま完了判定 → 実はスコープの一部がそもそも検証対象に入っていなかった

## CP-8: 根本原因は因果の実証をもって確定する（仮説ログ）

### 目的
トラブルシュートにおいて「もっともらしい説明を根本原因と誤認して満足する」誤診断を防ぐ。
誤診断は「失敗の繰り返し」として現れないため、試行回数のカウントだけでは検出できない。
確定の条件を「因果の実証」に置くことで、説明の説得力ではなく観測事実で判定する。

### ルール
1. **「根本原因を特定した」と記録できるのは、因果を実証したときだけ**。すなわち
   「原因をON/OFFすると症状が再現/消失する」ことを観測した場合に限る。
   それまでは必ず「仮説」と表記する。
2. 期待と異なる動作への修正試行では、**試行のたびに仮説ログを1行記録する**:

   | # | 仮説 | 予測（この修正で何が変わるはず） | 観測結果 | 判定 |
   |---|------|--------------------------------|---------|------|

   判定は「解決（因果実証済み）/ 仮説棄却 / 継続」のいずれか。
3. 記録せずに試行することは記録義務違反とする。仮説ログの行数をエスカレーション
   （規定行数で停止し人に報告・サブタスク化提案）の分母に使うことで、
   試行回数の自己申告問題を構造的に解消する。
4. 棄却した仮説とその理由も残す（同じ失敗ルートの再走を防ぐ）。
5. crash・失敗の観測では実行コマンド・環境・終了コードを必ず確認する
   （例: 124=timeout生存、139=真のSIGSEGV、127=ライブラリ不足）。
6. **観測は「主張を実際に働かせた」時だけ証拠になる。** pass/fail・ON/OFF を根拠にする前に確認する:
   - **デプロイ確認**: 変更が本当にビルド/再デプロイされたか（overlay・キャッシュ・prebuilt成果物・
     依存解決が古い物を配信していないか）。ソースを変えたつもりで古い成果物を測っていないか。
   - **前提と順序**: シナリオがバグの前提状態と実ユーザー動線の順序を再現しているか。
     前提を飛ばした「緑」は「バグ無し」の証拠にならない。
   - **観測手段の妥当性**: grep パターン・セレクタ等が結果を隠していないか。
7. **UI/描画の不具合はブラウザで実測する**（DevTools / JS-exec で computed style・DOM・console）。
   「HTTP 200・例外なし・画面が空/不可視」は、反証されるまで**セキュリティ既定値の silent block** とみなす。
8. 仮説ログは**否定した行の判定も更新**する（棄却を「解決」のまま放置しない）。修正の受入は
   「原因を OFF で消える」だけでなく「保護を ON に保ったまま最小設定で直る」まで確認する。
9. 在-harness で安定再現できない挙動は、**ユーザーの手動再現＋コード検査を ground truth** とし、
   恒久ガードは実装可能な別レイヤに回す。**非判別テスト（バグがあっても緑になるテスト）を足さない**。

### チェック方法
- worklog / investigation.md に仮説ログ表が存在し、「解決」判定の行に観測事実
  （コマンド・出力・終了コード）が紐づいていることを確認する。
- 「根本原因」という語が判定「解決」以前のエントリに現れていないか grep する。

### アンチパターン
- ❌ コード構造の分析だけから「根本原因を特定した」と宣言する（再現テストなし）
- ❌ 修正後に症状が消えたことだけで因果を確定する（環境要因の変化と区別できていない）
- ❌ 試行錯誤を自由記述で散発的に記録し、後から試行の系列を再構成できない

### 実例
あるデーモンプロセスの「SEGFAULT」に対し「ELF copy relocation + C++ static constructor の衝突」という
もっともらしい根本原因が一度確定として記録されたが、再調査の結果 SEGFAULT 自体が再現せず、
真因は (1) 共有ライブラリ検索パス未設定 (rc=127) と (2) 前提デーモン未起動による機能不全だった。
因果の実証（再現テスト）を確定の条件にしていれば、初回の誤診断の時点で検出できた。

## CP-9: 公式マイグレーションガイドを変換計画前に網羅確認する

### 目的
フレームワーク・ライブラリのメジャーバージョンアップグレードで発生する実行時障害の多くは、
公式マイグレーションガイドに既に記載されている。変換計画（work-plan / Transformation
Definition）を書く**前に**ガイドを網羅確認することで、障害を事前に防止する。
CP-1（changelog調査）のフレームワーク版・強化形。

### ルール
1. 現在のバージョンとターゲットバージョンを特定する
2. その間の**すべての**公式マイグレーションガイドを収集する
   （**多段メジャージャンプの場合、ガイドはバージョン境界ごとに複数存在する**。
   例: Struts 2.5→7.1 は「2.5→6.0」と「6.x→7.x」の2本）
3. 各ガイドから破壊的変更を全て抽出し、既存コードへの影響数をカウントする
4. 必要な設定変更・コード修正を work-plan に組み込む
5. ガイドのURLを計画に参照として記載する
6. **セキュリティ強化系のデフォルト変更に特に注意する**。コンパイルエラーにならず、
   実行時に例外も出さずに機能が失われる**サイレント障害**のパターンが多い
   （例: OGNLアローリストが空文字を返す、パラメータバインドが例外なしで不発になる）

### チェック方法
- work-plan に「参照ガイド」セクションがあり、バージョン境界ごとのURLが列挙されている
- ガイド記載の破壊的変更それぞれに「対応方法 or 非該当（理由）」が紐づいている

### アンチパターン
- ❌ 変換を実行してから実行時障害の調査でガイドに辿り着く（後追い）
- ❌ 最新バージョンのガイドだけ読み、中間バージョンのガイドを飛ばす
- ❌ コンパイルが通ったことでアップグレード完了と判断する（サイレント障害を見逃す）

### 実例
あるWebアプリケーションフレームワークの2メジャーバージョンをまたぐアップグレードで遭遇した実行時障害（パラメータバインド不発のNPE、
サーバサイド式言語のサイレント障害によるページタイトル空白、生成HTML要素IDの変更、ファイルアップロードの
サイレント障害）は、**ほぼ全てが公式ガイド2本に記載済み**だった。事前確認していれば防止できた。

## CP-10: 移行先スタックの事前検証（EOL/互換マトリクス/PoC）

### 目的
互換性のないライブラリ・フレームワークの組み合わせを選んで変換を開始すると、後工程で大きな
手戻りが発生する。**変換作業に入る前に**、移行先スタックの妥当性を検証するフェーズを設ける。

### ルール
1. **EOL / LTS 状況の確認**: 移行先候補の各コンポーネントがサポート期間内か、次のEOLがいつかを表にする
2. **互換マトリクスの作成**: フレームワーク間の必須依存関係を列挙し、矛盾がないことを確認する
   （例: 「フレームワークAのvXはランタイム基盤BのvY以上が前提」の連鎖に穴がないか）
3. **既存コードの依存度分析**: 移行先を変えた場合の影響範囲を定量把握する
   （grep等で影響ファイル数をカウント）
4. **最小構成PoC**: 選定した組み合わせでビルド＋最小ページ/機能＋認証等の基本フローが
   動くことを確認する
5. **破壊的変更の数による移行コスト見積もり**: 公式ガイド（CP-9）の破壊的変更リスト×
   影響ファイル数から工数を見積もり、段階実施か一括実施かを判断する

### チェック方法
- work-plan に EOL表・互換マトリクス・依存度分析の結果が含まれている
- PoC の成果（ビルドログ・起動確認）が 00-analysis または worklog に記録されている

### アンチパターン
- ❌ 「最新の組み合わせなら動くはず」と検証なしに変換を開始する
- ❌ メジャーバージョンを何段階もジャンプする影響を、破壊的変更の件数で定量化せずに見切り発車する

### 実例
言語ランタイム・Webフレームワーク・DIコンテナ・名前空間規約を同時に最新化する一括移行。
「フレームワークAの新版 → 名前空間規約Bが前提」「セキュリティモジュールの新版 → DIコンテナの新版必須」等の互換連鎖の
確認と破壊的変更の事前抽出（CP-9）を欠いたまま変換したため、実行時障害が多発した。
lessons-learned はこの事前検証フェーズを推奨ワークフローの筆頭（Step 0）に挙げた。

## CP-11: 移行対応台帳は「観点」を網羅の基準にし、件数は移行作業中に検出器で得る

### 目的

「プラットフォームが変わったのに直し忘れた箇所」を機械的に数え上げ、未対応をゼロにする。
期待リスト（CP-7）は**成果物の存在**を数えるが、既に存在する成果物の**中で**直し忘れた箇所は検出できない。

### ルール

1. **網羅の基準は「Playbook の観点表（`analysis-appendix.md`）のうち対象に該当する観点」にする。**
   コードのパターン走査ヒット数を網羅の基準にしない。**台帳の1行 = 1観点**である
2. **ツールチェーンが列挙できる観点（①強制）を事前に数えない。** 名前空間の置換・
   プロジェクトファイル形式・API リネームはビルドが数秒で正確に列挙する。
   **静的走査で先取りしても価値がなく、精度も劣る**
3. **事前に持つのは「②沈黙する観点」と「③誤誘導する観点」だけである**
   （②沈黙する: ビルドは成功し、実行時か本番でだけ壊れる。③誤誘導する: ビルドは失敗するが、素直な修正が別の何かを壊す）
4. **各観点は検出コマンドを携帯する。** 説明文だけの観点は全量が出ない。
   例: 「移行先は大文字小文字を区別する」を知らなければ参照パスの不一致は永久に0件のままで、
   **作業をしていても浮かび上がってこない**
5. **各観点の検出器には否定テストを付ける**（CP-13）
6. **件数は移行作業中に検出器を回して得る。** 検出器を回す → N件出る → 直す → 再実行して0 →
   verify で固定。**計画段階で全量を数値化して完了判定の分母にしない**
7. **検出手段を再実行可能な形で記録する**（`00-analysis/detection/` 等）。Phase 4 で再走査するため、手段が失われると検証が再現できない
8. **各行に観点 ID（`MP-N`）と `path:line` 根拠を持たせる**（CP-3。AIの要約だけを根拠にしない）。
   カタログに無い観点を案件中に発見した場合は `MP-` 無しで起票してよいが、Phase 4 で Playbook へ戻す
9. **`対応不要` と `代替実装` には理由を必須にする。** 機能喪失を伴うなら HOLD-1 + ADR
10. **`未対応` ゼロを Phase 4 の完了条件にする**（数える対象は**観点**である）
11. **観点表の取りこぼしを前提にする。** 「網羅した」と書かない。
    新しく踏んだ観点は**その案件で終わらせず Playbook の観点表へ戻す**

### なぜ走査ヒット数を網羅の基準にしないか（実測）

ある案件で走査ヒット数を網羅の基準にした結果、件数は **412 → 418 → 428 → 464** と**3回訂正され**
（いずれも外部からの反証。生成側は自力で気づけなかった）、**数える単位が観点ごとに違ったため**
（行 / 一意パス / ファイル）**増減比較ができなかった**。起票41行のうち**約24行はビルドが数秒で列挙し**、
ビルド通過時点で未対応は 41 → 9行、**残った9行はすべて「ビルドが沈黙する」項目**だった。
走査ヒット数は不安定・比較不能・案件固有で使い捨てである。
**台帳の1行を1観点にすると単位混在の問題そのものが消える**（コードのヒット数は行内の件数欄に入る）。

### 観点の書式と、網羅の基準の選び方

各観点は **ID（`MP-N`）/ リスク / 種類（②③）/ なぜ検出されないか / 検出コマンド /
正しいと言える観測（CP-4）/ 否定テスト（CP-13）** を持つ。書き方は
[docs/authoring-playbook.md](../docs/authoring-playbook.md)「観点表の書き方」にある。

観点表の**どれが該当するか**は移行の性質で変わるため、選択そのものは固定しない。代わりに
**「どの観点を選んだかを書くこと」を要求する**（`./verify.sh adaptation` が定義の存在を検査する）。
**AI が抽出した仕様・ルールの一覧を網羅の基準にしてはならない** — 抽出物の誤りは実コードの裏取りで
捕まるが（CP-3）、抽出物が**書かなかった**項目は抜け落ちたまま気づかれず、網羅率は裏取りで救済できない。

### 適用タイミング

| Phase | やること |
|-------|---------|
| 0b | **観点表から該当する観点を選ぶ**（規模とリスクの提示）。コードを数えない |
| 2 | 観点ごとに**検出コマンドと否定テスト**を用意する。work-plan と同時に台帳を起こす |
| 3 | Step ごとに**検出器を回して全量を得て**直し、`対応済` へ移す |
| 4 | 全検出器を再実行して `未対応` ゼロを確認する。**踏んだ新観点を Playbook の観点表へ戻す** |

### チェック方法

```bash
./verify.sh adaptation
```

### アンチパターン

- **ビルドが列挙する観点（①）を事前に静的走査で数える** — 精度が劣るうえ、同じ情報をビルドが数秒で出す
- **計画段階で全量を数値化して完了判定の分母にする** — 単位が混在して算術が成立しない
- **観点に検出コマンドを付けない** — 作業していても全量が浮かび上がらず、カウントが永久に0になる
- **観点表の全観点を採用する** — 該当ゼロの行が台帳を薄め、「網羅した」という誤った感覚を生む
- **検出手段を使い捨てにする** — Phase 4 の再検証が再現できない
- **踏んだ観点を案件内で終わらせる** — 次の案件が同じ発見を1から繰り返す
- 網羅の基準の定義を空欄のまま台帳の行を起こす — 何を数えたのか後から分からない

## CP-12: 検証ツールはホスト環境に問い合わせない形で書く

### 目的

移行の中心作業は「移行元と移行先の**差異**を検出する」ことである。その検出ツールが
**自分がどちらの環境で動いているかに影響される**なら、検出結果は信頼できない。
「差異を検出する道具が、まさにその差異の影響で無効化される」失敗を防ぐ。

### ルール

1. **実在・同一性の判定をホストのファイルシステムに委ねない。** 代わりに**一次情報**
   （`git ls-files` のファイル一覧・設定ファイル・マニフェスト）との**厳密な文字列比較**で判定する
2. 環境依存を持ち込む典型: `test -e` / `test -d` / パス解決 / 大文字小文字 / 改行コード /
   ロケール依存のソート / `realpath`。**いずれも「ホストに聞いている」**
3. **GNU 専用オプションを使わない**（作業ホストが macOS のことがある。BSD では挙動が違う）:

   | 禁止 | 移植可能な代替 |
   |------|--------------|
   | `sed -i`（接尾辞なし） | 一時ファイル経由（`sed ... > tmp && mv tmp f`）または `perl -pi -e` |
   | `grep -P` | `grep -E`（POSIX ERE）または `perl -ne` |
   | `readlink -f` | パスを文字列として扱う（正規化しない）／`python3 -c` |
   | `date -d` | `python3 -c` で計算する |
   | `stat -c` | `wc -c` / `git ls-files -s` 等で代替する |
   | `sort -V` | `sort -t. -k1,1n -k2,2n ...` に展開する |

4. **検出件数が「出ている」ことを正しさの根拠にしない。** 件数は水増し・取りこぼしの双方で誤る
5. **Playbook の差異カタログには「この差異を検出するツール自体が同じ差異の影響を受けないか」を
   確認する欄を設ける**

### チェック方法

```bash
# 検出スクリプト内の環境依存パターンを洗い出す
grep -nE 'test -[ed]|\[ -[ed] |realpath|readlink -f|grep -P|sed -i |date -d |stat -c |sort -V' \
  00-analysis/detection/*.sh
# 期待件数を一次情報から独立に算出し、スクリプトの出力と突合する
```

### アンチパターン

- ❌ ファイルの実在を `test -e` で判定する（大文字小文字を区別しない FS で偽陰性）
- ❌ 検出件数が出ていることを「検出できている」証拠として扱う
- ❌ 手元（macOS）で動いたスクリプトを移行先（Linux）の判定にそのまま使う

### 実例

静的アセット参照のパスが実ファイルの大文字小文字と一致せず Linux で 404 になる箇所を検出する分類で、
最初の実装は `[ -e "app/Bookstore.Web/$rel" ]` で実在を判定していた。macOS の既定 FS は
大文字小文字を区別しないため `Content/images/...` を「実在する」と判定し、**検出できなかった**。
さらに別のバグ（`grep -n` の行番号をパスとして扱っていた）で **21件という水増しの数字が出ており、
「検出できているように見えて」いた**。数字が出ていたことが誤りの発見を遅らせた。
`git ls-files` の実ファイル名との厳密比較（`grep -qFx`）に変更して正しく4件を検出した。
同じ案件では `grep -P` でも踏んだ（BSD grep は `-P` を持たない）。

## CP-13: 検出器には否定テストを付ける（人手の独立検証を機械検査で置き換える）

### 目的

**「0件」は「無い」とも「検出できていない」とも読める。** 検出器が本当に検出できることを、
壊して確かめるまで検出能力は未証明である。これを義務化すると、**人手の独立検証が担っていた役目
（検証器そのものを疑う）を、機械的・再実行可能な形で置き換えられる。**

CP-12 は「検出器がホスト環境に問い合わせない形で書かれているか」（書き方）を扱う。
CP-13 は「その検出器が本当に検出できるか」（能力の証明）を扱う。CP-8 の因果の実証は
**原因の確定**が目的であり、こちらは**検査器の能力**が対象である。

### ルール

1. **各検出器に否定テストを1つ以上付ける。** 検出されるべき状態を意図的に作り、
   **EXIT≠0（または件数が増える）ことを確認する**
2. **否定テストは「測りたい失敗と同じ解析段階」で行う。**
   コンパイラの検出能力を測るなら**構文エラーではなく意味エラー**を注入する
   （構文エラーはパース段階で報告され、意味解析まで到達したことを証明しない）
3. **否定テストの結果を記録する。** 「実施した」ではなく**何をどう壊して何が出たか**を書く。
   記録は `docs/decisions/decisions.md` の「否定テストの記録」節に、観点 ID（`MP-N`）付きで残す
4. **検査器自身の欠陥を疑う。** 否定テストは被検査物ではなく**検査器の能力**を測るものである
5. **`未対応` ゼロを宣言するときは、台帳に現れる全観点の否定テスト記録があることを条件にする**
   （`./verify.sh adaptation` が観点 ID の集合を突き合わせる）

### 何を疑うか（検証妥当性のチェックリスト）

否定テストで確かめるのは「検出器が主張を判別できているか」である。事故はここに集中する。

- **ON/OFF が同一の成果物を測っていないか**（成果物の重ね合わせ・install 済みの旧成果物・キャッシュ）
- **観測手段自体が妥当か。** grep が境界で切れて成功を「空」と誤認していないか。**非空アサーション**があるか
- **テストがバグの発火条件を満たしているか。** 実ユーザー動線の**順序・前提**を再現しているか
- **保護をONに保ったまま直っているか**（セキュリティ機構を全体OFFにして直したものを採用していないか）

### なぜ人手の独立検証を置き換えられるか

独立検証（隔離した反証者に「この宣言を偽だと示せるか」を試させる手法）は実際に欠陥を出すが、
コストが高く**一度しか回らない**。否定テストは同じ役目を果たしながら**恒久的に回り続ける。**

| | 人手の独立検証 | 検出器の否定テスト |
|---|---|---|
| コスト | 反証者の準備・実行・裁定・記録 | 1コマンド |
| 再実行 | **不可**（一度きり） | **無限に再実行可能** |
| 対象 | 文書と数値 | **検出器の検出能力そのもの** |
| 記録 | 数千字 | EXIT コード |

**実測**: 人手の独立検証が出した findings 約29件のうち**約15件は「事前に作った分析成果物の
記帳ミス」**（件数の誤り・ID 衝突・網羅の基準の抜け・単位の不統一）で、重い事前分析を作ったからこそ
生まれた欠陥だった。CP-11 の改訂で成果物そのものが消える。同じ案件で否定テストは、被覆率検査器の
`pipefail` × SIGPIPE による偽陰性（**11% と報告されていたが実は 100%**）、走査パターンの取りこぼし、
**一致検査器自身の欠陥**（記入例を実データとして拾っていた）、コンパイラが型不整合を**3箇所のうち
1箇所しか指摘しない**ことを見つけた。

**人手の独立検証を残すのは「移行完了宣言」と「HOLD-1 の機能除外」の2つだけである**
（手順は [harness/skills/migration-adversarial-review](../harness/skills/migration-adversarial-review/SKILL.md)）。
新しい移行経路の観点表の構築は**レビューではなく一次情報調査**であり、検出器では発見できない。

### チェック方法

```bash
# 検出器を壊して EXIT≠0 になることを確認する（0 なら検出能力なし = 検出器の欠陥）
cp detector.sh /tmp/neg.sh   # 期待値やパターンを意図的に壊す
bash /tmp/neg.sh; echo "EXIT=$?"

./verify.sh adaptation       # 台帳の観点 ID と否定テスト記録の突合
```

### アンチパターン

- **0件を「対応済」の根拠にする** — 検出できていないだけの可能性が残る
- **構文エラーで意味解析の到達を確かめる** — 段階が違うため証明にならない
- **検出器を書いた本人が「動くはず」で済ませる** — 検査器の欠陥は否定テストでしか出ない
- **否定テストの結果を「実施した」とだけ書く** — 何をどう壊して何が出たかが再現できない
