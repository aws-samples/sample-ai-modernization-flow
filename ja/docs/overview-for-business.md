# かんたん解説（IT部門・非エンジニア向け）

技術的な詳細は[for-engineers.md](for-engineers.md)、使い方は[how-to-use.md](how-to-use.md)を参照。

---

## 1. ひとことで言うと

本フローは、古い技術で作られたシステムの移行を、AIエージェントに決められた手順で進めさせるための枠組みである。

AIに「移行して」と任せきりにすると、ビルドは通るのに機能が抜け落ちていることがある。なぜそのように直したのかが、後から誰にも分からなくなることもある。
本フローでは、AIが自律的に進めてよい範囲と、人が判断すべき節目をあらかじめ分けておく。
そのうえで、判断の根拠を記録に残しながら移行を進める。

## 2. こんな困りごとに

| 困りごと | 本フローの対応 |
|-----------|--------------|
| サポート切れの技術で動いていて、移行したいが規模が読めない | アセスメントだけで止められる（第3節の特徴1を参照） |
| 設計書が古く、現行の仕様が分からない | 現行コードの振る舞いを、実行できるテストとして記録する。このテストは現状の入出力を固定する |
| AIに任せると、動いているように見えて機能が抜けていないか不安 | 手を入れる必要がある箇所を台帳にまとめる。対応を説明できていない箇所の件数をゼロにすることを完了条件とする |
| なぜこの実装になったのか、後から誰にも分からなくなる | 設計判断を記録（ADR）として残す。判断の節目では必ず人の承認を求める |
| 作業中に判明したシステム固有の知見が、AIとの対話の中で失われてしまう | 作業中の学び（Lessons Learned）と、移行作業をよりよく進めるための知見（Practice）を、ドメイン知識として記録する |
| 移行が長期化し、担当が変わると引き継げない | 作業状態・判断・知見をファイルに残し、中断と再開ができるようにする |

## 3. 5つの特徴

### 特徴1: アセスメントだけを行える

移行に着手する前に、現状を調べる作業だけを実施できる。作業を止められる時点は2つある。

| どこで止めるか | 受け取るもの |
|--------------|---------------------|
| ①分析 | リポジトリごとの現行構成の棚卸し、技術的負債の一覧、構造分析の結果（HTML形式で閲覧できる） |
| ②判断材料 | ①の成果物に加え、複数のリポジトリを統合したシステム全体の構成図、移行先の候補と比較、概算規模、主要なリスク、移行方針の案 |

### 特徴2: 移行先はアセスメント結果を見てから決める

現行の技術構成は分析で明らかになる。移行先は、その分析結果を見てから決める。
この順序にすることで、先に移行先を決めて後から無理があると分かる事態を避けられる。
移行作業の途中でも、依存関係などの理由があれば、人の承認を得て作業計画（work plan）を変更できる。

### 特徴3: 完了は動作の証拠で判定する

各工程の完了は、テスト結果と観測結果で判定する。設計書が承認されただけでは、完了とはみなさない。
ビルドが通った段階もまだ未完了であり、実際に動かして動作を観測した時点で完了とする。

### 特徴4: 判断が必要な場面で必ず止まる

AIが独断で決めてはいけない事項を、あらかじめルールとして定めている。
たとえば機能を削る、データ形式を変える、作業範囲を変えるといった場面では、AIは必ず作業を止める。
そのうえで選択肢と影響をまとめ、人の判断を求める。

判断を待つあいだ、AIはその判断に関係しない別の作業を進め、待ち時間をできるだけ減らす。

### 特徴5: 機能が失われたことを検出する

移行で最も見つけにくいのは、機能が動かなくなっているのにエラーが出ない不具合である。
本フローでは、手を入れる必要がある箇所を一覧（台帳）にまとめ、移行後の実装と突き合わせる。
さらに、利用者が実際に行う操作の流れをブラウザで自動的に再現するテストを、検証の必須項目として組み込む。

## 4. 進め方（大きな流れ）

```
  ① 分析        Phase 0a  現行構成と技術的負債を分析する
  ② 判断材料    Phase 0b  移行先の候補と規模・リスクをまとめる
  ③ 準備        Phase 1   現行動作を記録し、検証の範囲を決める
  ④ 計画        Phase 2   作業計画を承認してもらう
  ⑤ 実施        Phase 3   段階的に移行し、各段階で検証する
  ⑥ 最終確認    Phase 4   全機能の検証と、第三者視点での再確認
```

各段階の終わりに、AIは次の段階へ進んでよいかを人に確認する。

## 5. できること・できないこと

| | 内容 |
|---|---|
| できる | アプリケーションコードに対する、現行構成の分析 / 技術的負債の洗い出し / 移行先候補の比較 / 段階的な移行の実施 / 検証の自動化 / 判断と知見の記録 |
| できない | 移行後の性能試験・障害試験（後続フェーズとして追加可能） |
| | クラウド環境の設計・構築（移行後の後続フェーズとして追加可能） |
| | AIがクラウド上の資源を直接操作する場合の統制（本フローは1台のサーバ内での作業を前提とする） |
| | 本番相当データをテストに使うかの判断（法令や契約が関わるため、常に人が判断する） |

## 6. 安心して利用できる理由

- 現行のソースコードは変更しない。現行コードは読み取り専用で扱い、移行後のコードは別の場所に作る
- 判断の記録が残る。「なぜこの技術を選んだか」「なぜこの機能を削ったか」を後から確認できる
- 中断しても続けられる。作業状態がファイルに残るので、担当の交代や日をまたぐ作業にも対応できる
- 検証は自動化される。目視確認に頼らず、機械的なチェックで合否を判定する

## 7. よくある質問

Q. 移行先の技術を決めていませんが、始められますか。
始められる。むしろ、分析結果を見てから移行先を決めることを推奨している。
開始に必要な情報は、対象のソースコードの場所と、変更してはいけないものの2つだけである。

Q. システムが複数のリポジトリに分かれています。
複数のリポジトリにも対応している。まず全体を棚卸しし、リポジトリごとの分析を並行して進める。
画面と業務処理のやり取りのようなリポジトリ間の連携部分は、後から変更するのが難しいので、早い段階で洗い出す。

Q. すでに別途分析を実施済みです。やり直しになりますか。
やり直しにはならず、既存の分析結果を取り込める。
ただし、分析した時点より現行コードが更新されていたり、分析が不十分だったりする可能性がある。
そのため、AIは現行コードをもとに分析結果を確認しながら作業を進める。

Q. どのくらいの期間がかかりますか。
期間は対象の規模と移行の内容によって変わる。参考までに、中規模のJava Webアプリケーション（150K LOC、既存テスト約160件）で技術スタックを更新した事例がある。
この事例では、分析が数時間で終わり、実装の完了までは人とのやり取りを含めて数日だった。
