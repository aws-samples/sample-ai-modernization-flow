# エンジニア向け解説

考え方は[concepts.md](concepts.md)、使い方は[how-to-use.md](how-to-use.md)を参照。
本ドキュメントでは、3階層の境界、知見体系、ゲートの実装といった内部設計を説明する。

---

## 1. 3行サマリ

- レガシー移行をAIエージェントに実行させるための3階層のフレームワーク。方法論（Method）、ドメイン知見（Playbook）、AI実行規律（Harness）で構成する
- 特定のツールに依存しない。グラフDBやベクターDBといったプラットフォーム基盤を持たず、利用者にも要求しない
- エージェントに守らせたい規則は、`verify.sh`（実行スクリプト）とgitで機械的に検査する

## 2. 3階層と再利用境界

| 階層 | ディレクトリ | 何が入るか | 新ドメイン適用時 |
|------|------------|-----------|----------------|
| Method | `method/` | Phase 0-4 のフロー、共通分析手順、共通プラクティス`CP-N` | そのまま使う |
| Playbook | `playbooks/<domain>/` | ドメイン知見`DP-N`、分析観点、verify実装例、reference、transform-config | 新規作成する |
| Harness | `harness/` | コア規律、skills、テンプレート、verify.sh雛形 | そのまま使う |

1つのプロジェクトに入るのは、共通部分と1つのPlaybookだけである。
そのため`DP-N`の番号はPlaybook間で重複してよい。たとえばclangのDP-3とjavaのDP-3は無関係である。

### Harnessの内部構成（実行規律のラダー）

```
harness/
├── core/migration-core.md     ← 常時ロード。薄く保つ（判断の骨格のみ）
├── skills/migration-*/        ← オンデマンドロード（SKILL.md 形式）
│   ├── migration-recording          記録フォーマット
│   ├── migration-troubleshooting    仮説ログと根本原因確定
│   ├── migration-adr                ADRドラフト・除外フロー・Phaseゲート
│   ├── migration-adversarial-review 独立検証（完了宣言・HOLD-1 に限る）
│   ├── migration-verification       検証ゲート運用
│   ├── migration-session            セッション開始/終了
│   ├── migration-subtask            サブタスク手順
│   └── migration-tree-setup         実装ツリー作成・2リポジトリ運用
├── templates/                 ← プロジェクト雛形
├── tools/                     ← hook から呼ばれる記録ツールと宣言ガード（既定で有効）
├── setup-modernized.sh        ← 実装ツリーの作成
└── verify.sh.template         ← 機械的強制の実体
```

ツリーの上から順に、常時ロード、オンデマンドロード、機械的強制の層が並ぶ。
強制が必要な規則ほど下の層に置く。プロンプトに書いただけの制約は、守られる前提にしない。

## 3. 知見体系（CP / DP / LL / ADR）

各IDの意味とワークスペースでの置き場所は、[how-to-use.md](how-to-use.md)の第4節で説明している。
フレームワーク側の原本は、`CP-N`が`method/practices-common.md`、`DP-N`が`playbooks/<domain>/practices.md`である。

### 採番権限の分離

無印の`CP-N`と`DP-N`を採番できるのは、フレームワーク本体だけである。自作のPlaybookでは、そのPlaybookの作者が採番する。
プロジェクトは`CP-<project>-N`と`DP-<project>-N`の名前空間で追記し、完了時に本体へ還元する。
フレームワーク本体への還元は、issueかPRで提案する（[CONTRIBUTING.md](../../CONTRIBUTING.md)）。欠番はそのまま残し、再利用しない。

この規則は実際の事故への対策である。稼働中のプロジェクトが独自に`DP-5`を採番し、Playbook本体の別内容の`DP-5`と衝突した。

### 昇格の3段

```
LL-N（プロジェクト固有）
  → 同ドメインの他プロジェクトでも使えると判断 → DP-<project>-N
    → 完了時の還元 → DP-N（無印。Playbook の作者が採番）
```

同じ教訓に別のプロジェクトでも当たった場合、その教訓はもうプロジェクト固有のものとして扱わない。

### 読む粒度

エージェントが既定で読むのは、各知見ファイルのSummary表だけである。本文は、該当するテーマの作業に入ったときに開く。
本文は人が読んで理解するための層なので、実例やアンチパターンを含めて詳しく書いてよい。

同様に、エージェントは`worklog.md`を時系列に通読しない。worklogは追記専用で、量が増え続けるからである。
前回の状態は`session-context.md`で把握する。

### 量の規律

文章で書いたルールは、エージェントの自己申告に頼るので守られないまま通過してしまう。
そのため知見の量は数値で上限を決め、`./verify.sh knowledge`で検査する。

| 対象 | 既定 | 超過時 |
|------|------|-------|
| サマリ1行 | 300 バイト | 一言に収まらないなら本文へ |
| 1エントリ本文 | 80 行 | 詳細を`reference/`へ分離し、本文に要点とポインタを残す |
| 1ファイルのエントリ数 | 15 件 | 統合を検討する。統合しない場合は`KNOWLEDGE-REVIEWED`として理由を記録すればPASSする |

## 4. 品質をどう担保するか

本フレームワークは、AIが生成したものを正しいと仮定しない。
4.1〜4.3の3層で生成物を検証できるようにし、4.4でその検証を担うモデルの割り当てを決める。

### 4.1 形式の健全性（verify.sh）

`verify.sh`は8段のゲートで構成されている。各ゲートは`./verify.sh <name>`で個別に実行できる。

| # | ゲート | 検査内容 | 適用条件 |
|---|--------|---------|---------|
| 1 | build | 期待リストの成果物が存在するか（CP-7） | work-plan確定後 |
| 2 | smoke | 起動・基本動作 | 同上 |
| 3 | integration | 連携・E2E。`REQUIRE_GOLDEN_PATH=1`ならgolden-path E2E必須 | 同上 |
| 4 | nonfunc | 非機能（opt-in） | 同上。かつ`RUN_NONFUNC=1`のとき |
| 5 | repo-sync | 両リポジトリの未コミット同期 / 未記録dirty / `DIAG-`・`STUB-`残存 / コミット時刻差 | 常時 |
| 6 | knowledge | 知見ファイルの量 | 常時 |
| 7 | adaptation | 移行対応台帳（網羅の基準の定義・根拠の有無・除外理由・未対応件数・否定テスト記録） | 常時 |
| 8 | project | プロジェクト情報の出所。`⟨inferred⟩`（AIの推定値）がwork-plan確定後に残っていないか | 常時 |

ゲートの適用条件は、`work-plan.md`に書かれた機械可読のマーカーで切り替わる。

```
<!-- WORK-PLAN-STATUS: DRAFT     -->  → 1〜4 は「未適用」として exit 0
<!-- WORK-PLAN-STATUS: CONFIRMED -->  → 本適用。期待リストが空なら build が FAIL
```

これにより、アセスメントだけで終える場合はゲート1〜4がFAILしない。
work-planの確定後は、期待リストへの成果物の登録漏れをbuildゲートが検出する。

### 4.2 網羅の基準（期待リストと移行対応台帳）

網羅したかどうかは、作業の前に数えられる基準を作り、その基準で判定する。
「主要な部分は見た」という定性的な判断は使わない。

| 対象 | 網羅の基準 | 実体 |
|------|-----------|------|
| 成果物 | 期待リスト | `verify.sh`の`EXPECTED_ARTIFACTS`。work-plan確定時に全数登録（CP-7） |
| 振る舞い | 移行対応台帳 | `01-plan/adaptation-ledger.md`。処理区分つき |

移行対応台帳の処理区分は、`対応済` / `代替実装` / `対応不要`（理由必須）/ `未対応`の4種類である。
`未対応`の件数をゼロにすることが、Phase 4の完了条件になる。

移行対応台帳の網羅の基準には、Playbookの観点表（`analysis-appendix.md`）のうち、対象システムに該当する観点を使う。
台帳の1行が1つの観点に対応する。コードを走査したときのヒット数は、網羅の基準にしない。
各観点の件数は、移行作業中に観点ごとの検出器を実行して得る。その理由は`practices-common.md`のCP-11に書いてある。

期待リストは、存在すべき成果物がそろっているかを数える。ただし、既存の成果物の中に修正し忘れた箇所があっても検出できない。
移行対応台帳は、その検出漏れを補う。

### 4.3 内容の正確性（検出器の否定テストと、狭く絞った独立検証）

`verify.sh`が担保するのは形式である。テストが本当に主張の正誤を判別できているかは、別の仕組みで担保する。
既定の手段は機械的な検査である。

| 対象 | 扱い | 通過条件 |
|------|------|---------|
| すべての観点の検出器 | 否定テスト（CP-13） | 検出器を壊してEXIT≠0になることを確認し、記録する。再実行可能 |
| 完了宣言 / HOLD-1 機能除外（不可逆） | 独立検証（別コンテキストのAI） | 実施は1回。findingsは台帳に起票し、処理区分を付けて閉じる。再検証はverify.shと否定テストで行う。機能除外の検証は1件ずつ軽く行う |
| work-plan確定（Phase 2→3） | 適用しない | work-planの行はPhase 3でも変更できる。計画の誤りはビルドとgolden-path E2Eで検出できる |

否定テストでは、検出器の検出能力を測る。検出されるべき状態を意図的に作り、検出器がEXIT≠0を返すことを確認する。
どの観点を疑うべきかのチェックリストはCP-13にある。

独立検証で最も重要なのは、検証するAIのコンテキストを生成側から隔離することである。役割名を分けるだけでは足りない。
反証を試みるAIには、検証対象の宣言と一次情報の所在だけを渡し、生成側の推論やworklogは渡さない。
検証の観点は2つある。1つは機能欠落で、スタブや無効化を独立に探索し、台帳と実装の差集合を取る。
もう1つはスコープで、成功基準から消えた項目が承認済みかを確認する。

独立検証は1回だけ実施する。検証の対象は、実装ツリーとその実行時の挙動に限る。
台帳の書式、ADRの配置、`verify.sh`自身の欠陥はfindingsにしない。
記録が増えるほどfindingsも増えるような指標は、完了判定には使えないからである。
運用の詳細は`skills/migration-adversarial-review`にある。

### 4.4 モデルの割り当て（判断と量で分ける）

モデルの割り当ては、作業で支配的な性質が判断か量かで決める。
サブエージェントかメインのエージェントかという区別は、割り当ての基準にしない。

| 対象 | 支配的な性質 | 割り当て |
|------|------------|---------|
| Tier 0（work-plan内の実装・ビルド・テスト・調査） | 量 | 速いモデルで可 |
| Tier 1（worklog・記録・コミット・和訳・台帳転記） | 量 | 速いモデル推奨 |
| Tier 2（HOLD）・ADR判断・HOLD-1除外・work-plan確定・独立検証・否定テストの設計 | 判断 | 強いモデルを維持 |

独立検証を行うサブエージェントは判断をしている。委譲先のサブエージェントであっても、より軽いモデルに切り替えてはならない。

## 5. 意図せぬ機能欠落の機械検知

移行で最も見つけにくいのは、例外が出ず、HTTP 200が返り、画面が空になるという症状のない不具合である。
build、unit、smokeの各テストは、起動して例外が出ないことしか確認しないので、この不具合を検出できない。

本フレームワークは、この不具合を4つの仕組みで検出する。

1. `// STUB-<id>:`マーカーの義務化: 一時的なスタブ・モック・無効化にはこのマーカーを付ける。
   コミット済みのコードにマーカーが残っていれば、`repo-sync`がFAILを返す（`// DIAG-<id>:`と同じ仕組み）
2. 禁止パターンゲート: `not implemented`などのパターンを検出する。パターンの定義は言語やフレームワークで異なるので、Playbook層に置く。
   走査対象は実装ソースに限定し、テスト用のモックを誤検知しないようにする
3. golden-path E2Eの必須化: `REQUIRE_GOLDEN_PATH=1`のときにgolden-path E2Eが未登録であれば、integrationゲートがFAILを返す
4. 移行対応台帳との突合: 機能が消えていれば、対応する行が`対応済`にならないので、未対応の件数として表れる

## 6. 中断耐性

長時間の移行では、セッションの切断が必ず発生する。記録の義務を作業完了時に課す設計では、途中で中断された調査の内容が失われる。

そのためAIは、最初の変更を行う前に`session-context.md`へ`- **This turn (<時刻>):** …`の形で宣言を1行書く。
この着手時の宣言は`preToolUse` hookで強制する。この強制は既定で有効になっている（詳細は[../harness/README.md](../harness/README.md)）。

また、状態を未コミットの作業ツリーだけに残さない。`[wip]`や`[diag]`の小刻みなコミット、`// DIAG-<id>:`マーカー、`session-context.md`の作業ツリー台帳で、状態をgit側にも残す。
記録のない未コミット変更があれば`repo-sync`がFAILを返すので、人が気づくかどうかに依存しない。

## 7. 複数リポジトリ

本フレームワークは、1つのシステムが複数のリポジトリで構成される場合にも対応している。

Phase 0aはリポジトリの棚卸しから始まる。棚卸しでは`.git`の有無だけに頼らず、ビルドルートも検出する。
分析はリポジトリごとに1回ずつ実行し（CCA = ATXの`AWS/comprehensive-codebase-analysis`）、リポジトリ間は並列で実行する。
並列実行の単位はgitのwork treeである。ATXは対象リポジトリで`git checkout -b`を実行するので、同じwork tree内では並列に実行できない。
1つのリポジトリを分けて並列に分析する場合は、`git worktree`かcloneで別のwork treeを用意する。

分析の進行状態は、実行台帳`analysis-runs.md`だけに記録する。
実装ツリーもリポジトリごとに1つ作り、`verify.sh`の`MODERNIZED_TREES`にすべて列挙する。
単一リポジトリの構成は、リポジトリ数が1の場合として同じ手順で扱い、専用の分岐は作らない。

## 8. ツール対応

| ツール | コア規律 | skills |
|--------|---------|--------|
| Kiro (CLI/IDE) | `.kiro/steering/` | `.kiro/skills/`（自動認識） |
| Claude Code | `CLAUDE.md` | `.claude/skills/`（Agent Skills） |
| その他 | 各ツールのルールファイルに core をコピー | skills を参照ドキュメントとして指示 |

本フレームワークは、1つのエージェントが逐次に作業する環境だけでも完全に機能する。
並列実行や独立検証は、効率や検証の強度を高めるためのオプションである。
これらを使えない環境では、別セッションでの検証、さらに人のサインオフへと段階的に代替する。

## 9. 本フレームワークが担わないこと

| 範囲 | 理由 |
|------|------|
| デプロイ環境の設計・構築 | Phase 4後の後続タスクとして扱う。ただし実際の移行では必ず発生し、ターゲット環境の制約によってアプリの改修が必要になることもある |
| クラウド操作のガードレール | 単一ホスト内の作業を前提としている。IAM境界やPolicy as Codeは別途整備する |
| 性能・リーク・耐障害性・セキュリティ | 既定でスコープ外とする。Phase 1で明示的にADRとして決める |
| 本番相当データの利用可否 | 常に人の判断（Tier 2）に残す |
