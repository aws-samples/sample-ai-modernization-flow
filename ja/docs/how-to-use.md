# 使い方

本ドキュメントは利用者向けに、セットアップから移行完了まで、どのように使うのかを、各段階で実際に起きることとあわせて説明する。
考え方は[concepts.md](concepts.md)、内部設計は[for-engineers.md](for-engineers.md)を参照。

---

## 1. 30秒でわかる全体像

あなたが「<ソースのパス> のアセスメントを開始します。Phase 0a から始めてください」と伝えると、AIは起動インタビューから始める。
起動インタビューでは、AIがソースを走査して分かる項目を埋め、足りない項目だけを1回にまとめて質問する。その後は次の順に進む。

| Phase | 何が起きるか |
|-------|------------|
| 0a | リポジトリ棚卸し → ATX分析（構造・技術的負債）→ 結果のHTML化 |
| 0b | 横断統合 → 移行先候補の整理 → 移行方針をADRで決定 |
| 1-2 | baseline取得 → 非機能スコープ決定 → 作業計画（work-plan）確定 |
| 3 | Step単位で実装 → 各Stepで`./verify.sh`全PASS → コミット |
| 4 | 全モジュール検証 → 台帳の未対応ゼロ → 否定テスト → 独立検証 → 完了 |

Phase 0a（分析結果）やPhase 0b（移行判断の材料）の時点で終えることもできる（第10節）。

開始に必要な情報は、対象ソースのパスと、変更してはいけないものの2つだけである。
移行先の技術スタックは未定でよく、Phase 0bで分析結果を見てから決める。

## 2. 3つのツリーと1つの記録リポジトリ

ワークスペースには次のディレクトリが並ぶ。AIエージェントはワークスペースルートで起動する。
Kiroの場合は`kiro-cli chat --agent migration`で起動する（第8節）。

```
<workspace>/                      ← ここでAIエージェントを起動
├── .kiro/steering/               ← コア規律 + プロジェクト固有情報
├── CLAUDE.md                     ← Claude Code用（同内容）
├── myapp/                        ← 対象ソース（読むだけ。内容は変更しない）
├── myapp-modernized/             ← 実装ツリー（Phase 3 Step 1 で作成）
└── myapp-migration-20260901/     ← 記録リポジトリ（計画・記録・検証）
```

| ツリー | 役割 | 誰が変更するか |
|--------|------|--------------|
| 対象ソース | 現行コード。参照専用 | コードの内容は誰も変更しない（`git init`とATXが作る作業ブランチだけを許可） |
| 実装ツリー | 移行後のコード | AIがコードを書く |
| 記録リポジトリ | 計画・記録・検証ゲート | AIが記録を書く。あなたはここを読む |

コードと記録を別のリポジトリに分けているのは、一方だけがコミットされて他方が未コミットのまま残った状態を機械的に検出するためである。
検出には`./verify.sh repo-sync`を使う。

1つのシステムが複数のリポジトリで構成される場合は、対象ソースと実装ツリーをリポジトリごとに並べる。
記録リポジトリは1つのままである。

## 3. あなたが触るファイル

installは多数のファイルを作成するが、あなたが読み書きするのはごく一部である。

| ファイル | あなたの関与 |
|---------|------------|
| `.kiro/steering/migration-project.md`（Claude Codeは`CLAUDE.md`） | AIが起動インタビューで埋める。あなたは質問に答えるだけ |
| `01-plan/work-plan.md` | Phase 2で承認する（内容はAIが書く） |
| `01-plan/adaptation-ledger.md` | 移行対応台帳。除外を判断するときに見る |
| `docs/decisions/decisions.md` | ADRを承認する。「なぜそうしたか」はこのファイルに記録される |
| `03-worklog/session-context.md` | 中断・再開時に状態を確認する |
| `verify.sh` | 実行して結果を見る（内容はAIが実装する） |
| `03-worklog/worklog.md` | 時系列の詳細。量が多いので通読せず、必要なときだけ読む |

`<PLACEHOLDER>`を手で埋める必要はない。AIは、埋められなかった項目だけをまとめて質問する。
AIが推定した値には`⟨inferred⟩`、あなたが確定した値には`⟨confirmed⟩`が付く。
`⟨inferred⟩`のままの値は仮説として扱われ、ADRや計画の前提には使われない。

## 4. 記録と知見の置き場所

作業中に出てくる`ADR-3`や`LL-2`といった番号は、次のファイルの項目を指す。

| ID | 何か | ワークスペースでの場所 | 誰が書くか |
|----|------|----------------------|-----------|
| `ADR-N` | 設計判断とその理由 | `docs/decisions/decisions.md` | AIが起草し、あなたが承認する |
| `LL-N` | このプロジェクト固有の教訓 | `docs/knowledge/lessons-learned.md` | AI |
| `CP-N` | ドメインに依存しない共通の知見 | `docs/knowledge/practices-common.md` | フレームワークが提供する。プロジェクトは`CP-<project>-N`で追記する |
| `DP-N` | 移行経路ごとの知見 | `docs/knowledge/practices.md` | Playbookが提供する。プロジェクトは`DP-<project>-N`で追記する |

AIが既定で読むのは各ファイルのサマリ表だけで、該当するテーマの作業に入ったときに本文を開く。
あなたも、まずサマリ表から見ればよい。
他のプロジェクトでも使える知見は、プロジェクトの完了時にフレームワークへ還元する。
採番と還元の規則は[for-engineers.md](for-engineers.md)の第3節にある。

## 5. Phase 0-4 で実際に起きること

### Phase 0a: アセスメント（コード分析の実行）

AIはまずリポジトリを棚卸しし、分析対象をあなたに確認する（既定は全件）。
その後、対象リポジトリごとにAWS Transform customの構造分析`AWS/comprehensive-codebase-analysis`（構造・技術的負債）を1回ずつ実行する。

複数のリポジトリの分析は並列で実行され、1リポジトリあたり数十分かかる。
AIがバックグラウンドで実行してログを監視するので、あなたは待つだけでよい。

ATXはツールの仕様上、分析時に対象リポジトリへ書き込む。具体的には`.gitignore`への追記、作業ブランチの作成、コミットを行う。
そのため手順には、実行の前後でブランチとHEADが一致しているかを確認する作業が含まれている。

すでに分析結果がある場合は、分析を実行せずに結果を取り込む。
分析時点のコードが特定できなくても作業は止まらず、Phase 2で実コードを確認して補う。
分析を実行するのは、結果がないリポジトリだけである。

分析を実行する場合は、初回だけATXの準備が必要になる。ATXはCLIで使うことを前提としている。
AIは実行前に`atx`の導入状況、AWSの認証、リージョンを確認する。不足があれば[公式ドキュメント](https://docs.aws.amazon.com/transform/latest/userguide/custom-get-started.html)に沿って整える。
認証には、SSOかIAMロールの一時クレデンシャルを使うことを推奨する。

### Phase 0b: アセスメント結果の統合

AIはリポジトリごとの結果を、システム全体として読める形に統合する。
この段階で、リポジトリ間の契約（API・イベント・共有DB・共有ファイル）を棚卸しする。
frontendとbackendの境界は後から変更するコストが最も高いので、この段階で可視化しておく。

そのうえで、移行先スタックをADRとして決める。分析結果を見る前に決めてはならない。

### Phase 1: 準備

Phase 1では、依存ライブラリのchangelogの調査、baseline（現行の正常動作の記録）の取得、非機能要件のスコープ決定を行う。
非機能要件は、性能・リーク・耐障害性・セキュリティのそれぞれを「対象」と「対象外」に振り分け、ADRとして記録する。
この振り分けには、あなたの承認が必要である。

振り分けの目的は、「対象外」を明示的に決めることにある。実際に、メモリリーク検証の適用範囲が
実装の終盤まで決まらないまま放置された事例がある。

### Phase 2: 計画

AIはATXの指摘を実コードで確認し、作業計画（work-plan）を作る。
あなたが承認すると、AIが`work-plan.md`の状態を`CONFIRMED`にする。
この時点で、検証ゲートの扱いが「未適用」から本適用に切り替わる。

### Phase 3: 実装

AIはStep単位で実装し、各Stepで`./verify.sh`が全PASSしたら次のStepへ進む。
Tier 0の作業は確認なしで進み、Tier 2（HOLD）のトリガーに当たるとAIは作業を止めてあなたに判断を求める。

### Phase 4: 最終確認

Phase 4では、全モジュールのビルド、全テストの実行、baselineとの差分確認を行う。
移行対応台帳の未対応件数がゼロになり、独立検証の記録と全観点の否定テストの記録がそろった時点で完了となる。

## 6. 検証ゲートで機械的に検査される項目

`./verify.sh`は8段のゲートで構成されている。

| ゲート | 内容 | いつ適用されるか |
|--------|------|----------------|
| 1. build | 期待リストの成果物が存在するか | work-plan確定後 |
| 2. smoke | 起動・基本動作 | 同上（Step 1完了時に実装必須） |
| 3. integration | 連携・E2E。UIを持つアプリではgolden-path E2Eを必須にできる | 同上 |
| 4. nonfunc | 非機能（性能・リーク等） | 同上。ただしPhase 1で「対象」とした場合のみ |
| 5. repo-sync | 記録リポジトリと実装ツリーの同期、診断/スタブマーカーの残存 | 常時 |
| 6. knowledge | 知見ファイルの量（サマリ行・本文行数・エントリ数） | 常時 |
| 7. adaptation | 移行対応台帳（網羅の基準の定義・根拠の有無・除外理由・未対応件数）。未対応ゼロのときは独立検証と否定テストの記録 | 常時 |
| 8. project | プロジェクト情報の出所（`⟨inferred⟩`の残存） | 常時 |

各ゲートの適用状態は`./verify.sh status`で確認できる。

8段のゲートとは別に、`./verify.sh assessment`がある。
Phase 0aに着手済みであれば、`all`の最後にassessmentが自動で実行される。着手済みとは、`analysis-runs.md`に実行の記録が1行以上ある状態を指す。
この条件付きの実行は、機械的な確認を経ずにPhase 0aの完了を宣言できてしまうことを防ぐためにある。
assessmentはPhase 0aの完了条件を機械的に確認する。移行まで進む前提の案件では、Phase 0a完了時の人による確認をassessmentで置き換え、そのまま0bへ進める。
この置き換えが有効になるのは、`migration-project.md`の「アセスメントのみで終えるか」が`no`のときである。

work-planが未確定のあいだは、ゲート1〜4が「未適用」としてPASS扱いになる。
これにより、アセスメントだけで終える場合にゲートがFAILすることはない。
一方、work-planが確定済みなのに期待リストが空であれば、buildゲートはFAILする。成果物の登録漏れを見逃さないためである。

## 7. あなたが判断する場面（Tier と HOLD）

AIの作業は、後から元に戻すコストに応じて3段階に分かれる。

- Tier 0（自律実行）: work-plan内の実装・ビルド・テストは、`./verify.sh`が全PASSである限り確認なしで進む
- Tier 1（非同期レビュー）: 記録・コミット・Step間の遷移は、作業を止めずに行う。あなたは後からworklogやgit logでまとめて確認する
- Tier 2（HOLD）: 次の8つのトリガーのいずれかに当たると、AIは必ず作業を止めてあなたの判断を待つ

| # | 止まる条件 |
|---|-----------|
| HOLD-1 | 機能の除外・無効化・スタブ化（機能が失われる変更） |
| HOLD-2 | ワイヤーフォーマット・永続化形式・外部公開I/Fに触る変更 |
| HOLD-3 | 成功基準の変更（＝スコープ変更） |
| HOLD-4 | 同じ問題の試行が3回で未解決、または2セッション跨ぎ |
| HOLD-5 | 計画にない、まとまった追加作業の発生 |
| HOLD-6 | 破壊的操作・共有環境への変更・実行中の分析やビルドの停止 |
| HOLD-7 | ADR相当の設計判断 |
| HOLD-8 | Phase境界の通過 |

AIは作業を止めるとき、ADRドラフトなどの判断材料を添える。あなたは一言で承認できる。
判断を待つあいだ、AIはその判断に依存しない別の作業を進めてよい。保留中の判断はDecision Queueで管理される。

AIの宣言が正しいかを確かめる手段は2つある。1つは独立検証で、宣言したAIとは別のコンテキストのAIが、その宣言を反証できるかを試す。
もう1つは否定テストで、検出器を意図的に壊し、問題を本当に検出できることを確かめる。

独立検証を使う場面は限られている。独立検証は別のコンテキストで動くAIが行い、それが使えない環境では人のサインオフで代替する。

| 場面 | 扱い | 担保の手段 |
|------|------|-----------|
| 完了宣言 / 機能除外（HOLD-1） | 独立検証 | 実施は1回。findingsは移行対応台帳に起票し、処理区分を付けて閉じる。機能除外の検証は1件ずつ軽く行う |
| work-plan確定（Phase 2→3） | 適用しない | work-planの行はPhase 3でも変更できるので、確定は不可逆ではない。計画の誤りはビルドとgolden-path E2Eで高い精度で検出できる |
| 分析・計画途中のPhase境界 | 検出器の否定テスト | 各観点の検出器を意図的に壊し、検出できることを機械的に示す（CP-13）。残った指摘は台帳へ繰り越す |

この配分の根拠は[for-engineers.md](for-engineers.md)の4.3にある。

## 8. セッションが切れても続けられる仕組み

長時間の移行作業では、セッションの切断、サーバの再起動、日をまたぐ作業が必ず発生する。

- 状態を保持するファイルは`session-context.md`だけである。再開時はまずこのファイルを読む
- AIは着手時に、そのターンで何をするかを1行で宣言する。作業は途中で中断されるので、宣言は着手の時点で書いておく
- 状態を未コミットの作業ツリーだけに残さない。WIPコミットや診断コミットとマーカーで、git側にも残す
- 記録のない未コミット変更があると、`verify.sh repo-sync`がFAILを返す
- hookは、指示を受けた時刻と返答した時刻を、記録リポジトリの`03-worklog/turn-log.tsv`に毎ターン記録する。プロンプト本文は保存せず、このファイルはgitの管理対象外である
- AIは記録から作った表を`worklog.md`に貼る。表の列は指示・返答の時刻、所要（AIの処理時間）、待機（人の反応時間）、備考で、所要と待機の統計が続く。恒久的に残るのはこの表だけである
- 待機は前の返答から次の指示までの実時間である。人が考えていた時間とは一致しない
- Kiroでは`kiro-cli chat --agent migration`で起動しないと、何も記録されない
- ターン時刻の記録と着手時の宣言の強制は、既定でオンになっている。無効にする場合はinstall時に`--no-turn-log`または`--no-work-guard`を付ける（[../harness/README.md](../harness/README.md)）

これらは実際の事故を受けた対策である。ある案件では作業サーバが中断し、記録のない未コミット変更が2ファイル残った。
その結果、何をなぜ変えたのかをdiffから推測して作業を再構成する手戻りが発生した。

再開するときは、次のように指示すればよい。

```
作業を再開します。03-worklog/session-context.md を読んで前回の状態を確認し、続きから進めてください。
```

## 9. 困ったときの読み替え表

| 症状 | 見る場所 |
|------|---------|
| 今どこまで進んだか分からない | `03-worklog/session-context.md`のCurrent Status |
| なぜこの実装になったのか分からない | `docs/decisions/decisions.md`（ADR） |
| なぜこの機能がないのか分からない | `01-plan/adaptation-ledger.md`の`対応不要`行とADR |
| ゲートがFAILする理由が分からない | `./verify.sh <ゲート名>`を個別に実行してメッセージを読む |
| Phase 0aが終わったか判断できない | `./verify.sh assessment`を実行する。不足している記録が列挙される |
| ゲートが「未適用」と表示される | work-planが未確定である。Phase 2で`WORK-PLAN-STATUS: CONFIRMED`にする |
| AIが止まって判断を求めてきた | HOLD番号を見る（第7節の表）。ADRドラフトが添えられている |
| 同じ失敗を繰り返している気がする | `docs/knowledge/lessons-learned.md`と`practices*.md`のサマリ表 |
| 知見ファイルが大きくなってきた | `./verify.sh knowledge`が上限超過を報告する。内容を統合するか、超過の理由を記録する |
| `atx: command not found` / ATXの認証・リージョンエラー | 公式ドキュメントの導入手順に従い、Phase 0a-2cの確認をやり直す |
| 分析をやり直したくない | 既存の結果を取り込める（Phase 0a-2b）。結果のパスを渡すだけでよい |
| Kiroで`turn-log.tsv`の記録が増えない | `--agent migration`を付けずに起動している。第8節のコマンドで起動し直す |
| Windowsで`turn-log.tsv`が生成されない | hookが起動していない。[harness/README.md](../harness/README.md)の「Windowsで使う場合」を参照 |

## 10. アセスメントだけで使う

作業の終了点は3つある。

| 終了点 | 成果物 | 用途 |
|--------|--------|------|
| Phase 0a 完了 | ATX分析結果（HTML化済み）、リポジトリ棚卸し、実行台帳 | 分析結果そのものが欲しい。他チームへの引き渡し |
| Phase 0b 完了 | 横断統合、移行先候補、概算規模とリスク、移行方針ADRドラフト | 移行するかを判断したい |
| Phase 4 完了 | 移行済みの実装ツリーと検証記録 | 移行を完遂する |

`install.sh`の実行内容は、どの終了点を選んでも同じであり、モードの指定はない。
アセスメントで止めた後に移行へ進む場合も、再インストールは不要である。

## 11. 用語

| 用語 | 意味 |
|------|------|
| 対象ソース | 現行コード。参照専用で、内容は変更しない |
| 実装ツリー | `<product>-modernized`。移行後のコードを書く独立リポジトリ |
| 記録リポジトリ | `<product>-migration-<date>`。計画・記録・検証ゲートを置く |
| ATX | AWS Transform custom。Phase 0aのコード分析に使う |
| Playbook | 移行経路（例: .NET Framework → .NET）ごとの手順・観点・知見 |
| work-plan | Phase 2で確定する作業計画。Stepの並びと成功基準を持つ |
| ADR | 設計判断の記録（Architecture Decision Record）。背景・選択肢・決定・影響を書く |
| baseline | 移行前の正常動作の記録。移行後の比較の基準になる |
| 期待リスト | 移行後に存在すべき成果物の一覧（`verify.sh`の`EXPECTED_ARTIFACTS`） |
| 観点 / 観点表 | 移行で見落としやすい箇所の種類と、その検出方法。Playbookの`analysis-appendix.md`にある |
| 移行対応台帳 | 手を入れる箇所を観点ごとに管理する表（`01-plan/adaptation-ledger.md`） |
| 処理区分 | 台帳の各行の状態。`対応済` / `代替実装` / `対応不要`（理由必須）/ `未対応` |
| 未対応件数 | 台帳で`未対応`のまま残った件数。ゼロが完了条件 |
| golden-path E2E | 利用者の代表的な操作をブラウザで実行するテスト |
| 否定テスト | 検出器を意図的に壊し、本当に検出できることを確かめるテスト |
| 独立検証 | 作業したAIとは別のコンテキストのAIが、完了宣言などを反証しようとする検証 |
| findings | 独立検証で出た指摘。台帳の行として登録し、処理区分を付けて閉じる |
| Tier 0/1/2 | 自律実行 / 非同期レビュー / 同期ゲート（HOLD） |
| HOLD-N | AIが必ず作業を止めるトリガー（第7節） |
| Decision Queue | 判断待ちの事項の一覧。`session-context.md`にある |
| `⟨inferred⟩` / `⟨confirmed⟩` | AIの推定値 / あなたが確定した値 |
| CP / DP / LL | 共通知見 / ドメイン知見 / プロジェクト固有の教訓（第4節） |
