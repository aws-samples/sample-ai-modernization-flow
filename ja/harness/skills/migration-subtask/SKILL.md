# サブタスク手順

## 2段階（簡易＝宣言 + worklog / 重い＝サブタスク）

- **簡易調査（既定）**: session-context の `This turn` 宣言で着手を記録し、仮説ログと結論は
  worklog に書く（中間ファイルを作らない。skills/migration-troubleshooting）。
- **重い調査（本手順）**: HOLD-4/HOLD-5・Step跨ぎ・外部ツール導入に育ったら昇格する。昇格は
  `03-worklog/YYYYMMDDHHmm-<taskname>/` を作り、worklog に書いていた仮説ログを `investigation.md` へ
  移して `plan.md` を追加する（コミット・恒久保持）。

## トリガー

- ユーザーが「サブタスク開始: \<taskname\>」または「調査開始: \<taskname\>」と指示した場合
- HOLD-4（仮説ログ3行/2セッション跨ぎ）・HOLD-5（plan外作業）で提案し、承認された場合

## 手順

### 1. 作業ディレクトリ作成

```
03-worklog/YYYYMMDDHHmm-<taskname>/
```

- 日時は作業開始時点（`date '+%Y%m%d%H%M'`）
- taskname はユーザー指定の名前（英数字+ハイフン）

### 2. プラン作成

`03-worklog/templates/subtask-plan.md.template` をコピーして `plan.md` とし、以下を埋める:
- 目的（なぜこの作業が必要か）
- 対象（どのファイル/機能を扱うか）
- ステップ（具体的な作業手順）
- 成功基準（何が確認できれば完了か）

### 3. 作業実施

- 通常のTierゲート・作業品質ルール（コア規律）に従う
- **成果物・中間ファイル・ログ・外部ツール（git clone等）は全てサブタスクディレクトリ内に置く。**
  オリジナルソースや作業ディレクトリのルートを汚染しない
- トラブルシュート系は `investigation.md`（仮説ログ含む）と `results.md` を作成する
- **サブエージェントに一括ディスパッチする前に、必ず1件で試験する。** 割り当てられるツールは
  **役割（role）の指定で変わる**。ファイルI/Oを持たない役割を選ぶと全件が実行不能で返る
  （実測: 6バッチ全滅 → 役割を変えて1件試験してから再実行で解決）。試験で確認するのは
  「対象ファイルを1本読み書きできたか」だけでよい
- **サブエージェントのプロンプトには「捏造禁止・不能なら `FAILED: <理由>` と報告」を必ず含める。**
  読めなかった入力を推測で埋められると、成果物が「一見できているが虚偽」になる
- **委譲先だからといってモデルを落とさない。** 判断を含む作業（独立検証・ADR判断）は強いモデルを
  維持する。落としてよいのは量が支配的な作業（和訳・転記）だけである（コア規律「モデルの割り当て」）

### 4. 完了記録

- `03-worklog/worklog.md` にサマリを追記（日時 + タスク名 + 結果）
- `03-worklog/session-context.md` を更新
- **LL/DP棚卸し**: `results.md`作成と同じタイミングで、今回のサブタスクで得た教訓を
  `lessons-learned.md` / `practices.md`に反映すべきか確認する（該当なしも明示的に判定）
- gitコミット（Tier 1・非同期レビューゾーン: 指示を待たず実施）

## いつサブタスクにすべきか

- work-plan.md の Step に含まれない追加作業
- 複数のステップにまたがるトラブルシュート
- 外部ツールの導入・実行を伴う検証作業
- 作業プランを事前に定義してから実施すべき規模の作業

## サブタスクの価値（なぜ切り出すか）

- メインの作業コンテキストが試行錯誤のノイズで汚染されるのを防ぐ
- plan.md / investigation.md / results.md の構造が試行錯誤を再検証可能な形で残す
- 中断・再開が容易になる（session-context に「既存サブタスクで継続」と書ける）
