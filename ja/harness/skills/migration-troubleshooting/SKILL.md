# トラブルシュート規律 — 仮説ログと因果の実証

## 原則（CP-8）

**「根本原因を特定した」と記録できるのは、因果を実証したときだけ。**
すなわち「原因をON/OFFすると症状が再現/消失する」ことを観測した場合に限る。
それまでは必ず「仮説」と表記する。

- ❌ コード構造の分析だけから「根本原因」と宣言する（再現テストなし）
- ❌ 修正後に症状が消えたことだけで因果を確定する（環境要因の変化と区別できない）
- もっともらしい説明ほど危険。誤診断は「失敗」として現れないため、実証以外では検出できない

## 着手時に宣言する（中断耐性）

記録義務は完了時に発火するため、中断された作業（依頼を受けて深掘り中にセッションが切れる等）を守れない。
よって**最初の変更の前に**、そのターンの宣言を `03-worklog/session-context.md` の
「In-progress Investigation / Working-tree State」節に1行書く。

```
- **This turn (<T_prompt>):** <このターンで何をやろうとしているのか>
```

- `T_prompt` = そのターンの指示を受けた時刻。`./03-worklog/turn-report.sh --declare` が行ごと生成する
  （`--turn-log` を有効にしている場合）
- **`This turn (...)` は機械照合される共有アンカーである。** 日英で翻訳しない。
  `--work-guard` を有効にしていれば、宣言が無いうちは変更系ツールが hook でブロックされる
  （`Bash` / `execute_bash` は対象外なので抜け道は残る）
- **work-plan にある作業でも書く。** 守りたいのは「中断されたときに何をしていたか分かること」である
- 深掘りの内容（Trigger / Symptom / 何を観測できれば正しいか）は宣言の後に続けて書いてよい。
  **専用の scratchpad ファイルは作らない** — 恒久記録は worklog であり、
  中間ファイルは転記を1段増やすだけである。かさばる捨てる前提の中間データは `/tmp` で足りる

**未コミット変更の分類は同じ節の作業ツリー台帳に書く**（diagnostic(revert) / candidate-fix(verify)）。
**進行中の状態を未コミット作業ツリーだけに残さない**: 実装ツリーに `[wip]`/`[diag]` を小刻みにコミット
（中断しても `git log` + 台帳で再構成できる）。一時診断コードには **`// DIAG-<id>:`**
（id は台帳と対応）を付け、grep 可能にする。

**重い調査はサブタスクへ**: HOLD-4/HOLD-5・Step跨ぎ・外部ツール導入に育ったら
`03-worklog/YYYYMMDDHHmm-<taskname>/` を作り、仮説ログを `investigation.md` に移す
（コミット・恒久保持。skills/migration-subtask）。

**close-out（完了時）**:

1. **宣言行そのものを worklog へ写す**（仮説ログ・根本原因・判定と一緒に）。
   **これを省くと恒久記録に残らない。** 宣言は session-context にあり、同一セッション内で消すと
   間にコミットが無い限り git 履歴に入らない（実測: `git log -S` で0件）。
   **hook は宣言の存在を強制できるが、恒久化は強制できない。**
2. session-context の宣言と作業ツリー台帳を解消する
3. `grep -rn "DIAG-"` が 0・台帳に diagnostic 残なしを確認し、candidate-fix のみ検証後にコミットする

## 仮説ログ

修正試行のたびに1行記録する。記録場所: 小規模なら worklog.md、サブタスクなら investigation.md。

| # | 仮説 | 予測（この修正で何が変わるはず） | 観測結果 | 判定 |
|---|------|--------------------------------|---------|------|
| 1 | 共有ライブラリが見つからない（C/Unixの例） | パス設定でrc=127が解消するはず | rc=0で正常出力 | 解決（因果実証） |

- 判定: **解決（因果実証済み）/ 仮説棄却 / 継続** のいずれか
- 記録せずに試行することは記録義務違反
- 棄却した仮説と理由も残す（同じ失敗ルートの再走を防ぐ）

## エスカレーション（HOLD-4）

以下のいずれかに達したら**停止**し、仮説ログ全体と誤診断の可能性を添えてユーザーに報告、
「サブタスク開始: \<taskname\>」を提案する:
- 同一問題の仮説ログが**3行**に達しても判定「解決」に至らない
- 同一問題が**2セッション**にまたがった

仮説ログの行数がカウントの分母になるため、「試行を細かく刻んで回数を誤魔化す」ことはできない
（刻んだ分だけ行が増える）。

## 観測の基本

- **終了コードを必ず精査する**（ネイティブ実行の例）: 124=timeout（プロセスは生存＝起動成功の可能性）、
  139=128+11（真のSIGSEGV）、127=コマンド/ライブラリ不足、1=アプリレベルエラー
- crash報告は「実行コマンド・環境変数・終了コード」の3点セットで記録する
- デーモンの機能不全とcrashを区別する（起動して沈黙 ≠ SEGV）
- 環境要因（PATH, LD_LIBRARY_PATH, 前提デーモン, ディレクトリ権限）を仮説リストから外さない

## 長時間コマンドの監視

ATX実行・大規模ビルド等の長時間コマンドは、実行時間の長さだけを理由に手動実行を
依頼しない（対話操作が必須な場合を除く）。`while pgrep ...; do sleep; done` のような
単純な生存監視だけに頼らない（プロセスが消えたことは「正常終了」を意味しない。
異常終了でも消える）。

監視は1〜2分間隔で能動的に確認するサイクルとし、一度に長時間ブロッキングする
単一コマンドに丸投げしない。各サイクルで次を確認する:
- ログの最新数行（進捗の可視化。手動実行時の画面出力の代替になる）
- ログファイルの最終更新時刻（stale検知。一定時間更新がなければ停滞を疑う）
- プロセスの生存確認と、消えていた場合の終了コード
- ログ内のエラーパターン（`error:`, `Error [0-9]`, `undefined reference` 等）

異常（停止・停滞・エラーパターン検出）を確認したら、監視を続けず直ちに詳細確認に切り替える。

## 実例（教訓 — C/Unix移行の例）

あるデーモンプロセスの「SEGFAULT」誤診断: 「ELF copy relocation + C++ static constructor の衝突」
というもっともらしい根本原因が確定として記録されたが、再調査で SEGFAULT 自体が再現せず、
真因は (1) 共有ライブラリ検索パス未設定（rc=127）(2) 前提デーモン未起動による機能不全だった。
因果の実証を確定の条件にしていれば初回で検出できた。
