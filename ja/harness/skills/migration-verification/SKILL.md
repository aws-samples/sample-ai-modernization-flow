# 検証ゲート運用詳細

## 全8ゲート

ゲートは2群に分かれる。**適用条件は `work-plan.md` の機械可読マーカーで切り替わる。**

```
<!-- WORK-PLAN-STATUS: DRAFT     -->  → 下記の第1群は「未適用」として exit 0
<!-- WORK-PLAN-STATUS: CONFIRMED -->  → 本適用。期待リストが空なら build が FAIL（CP-7）
```

適用状態は `./verify.sh status` で確認できる。

**`./verify.sh assessment`** は上記8ゲートとは別で、**Phase 0a の完了条件を機械確認する**
サブコマンドである。**`all` からは条件付きで自動実行される**: `00-analysis/analysis-runs.md` に
分析実行の記録が1行以上あれば（= Phase 0a に着手済みなら）実行し、0件なら実行しない
（無条件に入れると初日から落ちて「落ちて当然」の慣れを生むため）。適用状態は
`./verify.sh status` に表示される。棚卸しの記入・対象外の理由・0a-2 の利用者確認・
分析実行の終了コードと出力先・git の復帰確認・成果物の入口・記録の更新を見る。
移行に進む前提の案件（`migration-project.md` の「アセスメントのみで終えるか」が `no`）では、
**0a 完了時の人間による確認をこれで置き換えて 0b へ直行する。**

### 第1群: work-plan 確定で適用が切り替わる（成果物と動作）

| ゲート | 内容 | 実装時期 |
|--------|------|---------|
| build | 期待成果物の存在確認（期待リスト方式） | work-plan確定時（初日）に全登録 |
| smoke | 起動・基本動作（例: CLIの--help、プロセス生存、依存解決。実装例はPlaybookのverify-snippets.md） | **Step 1完了時（必須）** |
| integration | 連携・E2E動作（02-test/integration/*.sh を呼ぶ）。`REQUIRE_GOLDEN_PATH=1` なら golden-path E2E が必須 | 各Stepで追加 |
| nonfunc | 非機能（opt-in。Phase 1のADR判断で「対象」の場合のみ） | 対象項目確定後 |

### 第2群: 常時適用（記録と規律）

work-plan の状態に関わらず Phase 0 から効く。**記録なき違反だけを弾く**設計であり、
理由を記録すれば通る（判断は人に残す）。

| ゲート | 内容 | 記録すれば通るマーカー |
|--------|------|--------------------|
| repo-sync | 記録リポジトリと全実装ツリーの未コミット同期、未記録 dirty、コミット済み `DIAG-`/`STUB-` の残存、禁止パターン、コミット時刻差 | `REPO-SYNC-DIVERGENCE-OK` |
| knowledge | 知見ファイルの量（サマリ1行300バイト / 本文80行 / 15エントリ） | `KNOWLEDGE-REVIEWED` |
| adaptation | 移行対応台帳（網羅の基準の定義の欠落、根拠 `path:line` の欠落、対応不要・代替実装の理由欠落、未対応件数の報告）。未対応ゼロ時は**独立検証の記録**と**台帳の全観点の否定テスト記録**を要求（CP-13） | — |
| project | プロジェクト情報の出所（work-plan 確定後に `⟨inferred⟩` が残っていないか） | `INFERRED-REMAINS-OK` |

## 期待リストの原則（CP-7）

- **スコープ内全成果物を work-plan 確定時に登録する。** まだビルドできないものも先に登録する
  （未登録の成果物は「ビルドされていない」事実そのものが検出されない）
- 期待リストの変更＝スコープ変更＝ HOLD-3（Tier 2・停止確認ゾーン）
- 除外した成果物はコメントとして理由（ADR-N）つきで残す

## 完了判定のルール

- `./verify.sh` 全PASSしない限り「完了」と記録しない（CP-4, CP-6）
- Step完了時に work-plan の成功基準テーブルと突合し、テスト漏れがないことを確認する（CP-6）
- 検証ゲートファイルはビルドシステムに上書きされない名前にする（`verify.sh` + `make -f`）

## テストで確認するまで「完了」と言えない変更

- 固定文字列・定数値の変更
- 条件分岐の片方のみ実行されるコード
- 設定値のデフォルト変更
- SSL/TLS関連の変更

## アドホックテストの記録と昇格

verify.sh 以外の個別テスト（起動確認、strace、プロパティ確認等）を行った場合:

1. `02-test/test-results/` に結果ファイルを作成する（`<stepN>-<テスト名>.md`）
   - 内容: テスト日時、目的、前提条件、手順（コピー実行可能な形式）、結果テーブル、判定
2. 再現可能な場合は `02-test/integration/` に再現スクリプトを作成する
   - スクリプトは「前提条件セットアップ→実行→観測→PASS/FAIL判定（rc=0がPASS）」を自己完結させる
3. **スクリプト化したら verify.sh の INTEGRATION_TESTS に登録する**（プロンプト頼みの検証をゲートに昇格）

記録の基準:
- 「ビルド成功」以上の確認（プロセス起動、RPC登録、出力確認等）を行った場合は記録対象
- verify.sh の実行結果のみで判定できる場合（バイナリ存在確認等）は記録不要

## テスト環境の前提条件

- テストに必要な前提（デーモン起動、環境変数、ディレクトリ、権限）は `02-test/test-procedures.md` の
  「前提条件」セクションに明文化する。揮発する前提（再起動で消えるもの）はセッション開始手順にも含める
