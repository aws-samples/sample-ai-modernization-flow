# ADR・Tier 2（HOLD）停止の実施手順

## ADRドラフト定型（軽量停止プロトコル）

HOLD-1/HOLD-2/HOLD-7 で停止するときは、以下の定型4節のドラフトを提示する。
ユーザーが一言で承認・修正・却下できる粒度にまとめる:

```markdown
## ADRドラフト: <タイトル>

- **背景**: <なぜこの判断が必要になったか。観測事実ベースで>
- **選択肢**: (1) ... (2) ... (3) ...（各選択肢の影響・機能喪失の有無・互換性を1行ずつ）
- **決定案**: (N) を推奨。理由: <なぜ>
- **影響**: <この決定が以後の作業に課す制約。将来の変更コスト>
```

- 承認されたら `docs/decisions/decisions.md` の `ENTRIES END` マーカー直前に正式記録する
  （`grep -n '^<!-- ENTRIES END -->$'` で行全体一致で探す）
  （判断日・フェーズを追加。採番は既存最大+1）
- **迷ったらADRを書いて止まる。ADRが多すぎることは咎めない**（書かない方が問題）
- **判断待ちの間、依存しない別作業（記録整備、次Step準備等）には進んでよい**

## Decision Queue 運用

保留中の判断は `session-context.md` の Decision Queue テーブルで管理する:

| # | 判断事項 | ADRドラフト提示日 | 状態 | ブロックしている作業 |
|---|---------|-----------------|------|-------------------|

- 判断が下りたら decisions.md に正式記録し、行を消す
- セッション終了時に未処理の Queue があれば、終了報告で明示する

## HOLD-1: 機能除外フロー

ビルドエラー等の解決で機能を無効化・削除する前に、必ず以下を経ること:

- a. 問題の事実を記述する（何が動かないか、なぜか）
- b. 選択肢を列挙する（修正 / 代替実装 / 除外 / スタブ化）
- c. 各選択肢の影響（機能喪失の有無、互換性）を明示する
- d. **ユーザーに確認する**（「この機能を除外してよいか？」）
- e. 判断結果を ADR に記録してから実装に進む

例外と原則:
- 「代替実装パスの選択」（同等機能を別手段で実現、機能喪失なし）は確認不要。ただし理由を説明する
- 機能そのものが失われる場合は必ず確認が必須
- **判断に迷った場合は「除外」側に倒して確認する**
- 除外した項目は work-plan の対象外テーブルと verify.sh のコメントに理由（ADR-N）つきで残す
- **移行対応台帳の該当行の処理区分を `対応不要`（理由必須）にする。** 台帳に反映しない除外は
  `./verify.sh adaptation` が「理由なし」として FAIL させる
- 一時的なスタブ化で済ませる場合は `// STUB-<id>:` を付ける（コミット済みに残ると repo-sync が FAIL）
- **除外の確定前に独立検証を行う**（skills/migration-adversarial-review）。除外は不可逆な宣言である。
  **1件ずつの軽い第二意見**でよく、全面掃引はしない

## HOLD-8: Phaseゲート定型確認

Phase境界（1→2→3→4）で停止し、以下を提示する:

1. **Phase完了条件チェックリストとの突合結果**（analysis-procedure / work-plan の完了条件）
2. **暗黙判断の掘り起こし**: 「このPhaseで暗黙に決めたこと（ADR未記録の判断）はないか」を
   自己点検する。判断の痕跡は worklog・コミットログ・除外テーブルから探す。
   あればADRドラフトを提示する（事後でも記録する — 後日の記録整備は正当な手順）
3. **ADR実績レビュー**: Decision Queue とADRログを提示。人が無修正で承認し続けているカテゴリが
   あれば、Tier 1（ドラフト作成+バッチレビュー）への降格を提案する。
   緩和は必ず実績データに基づく明示的なルール変更として行う（なし崩しの自動化をしない）
4. **ナレッジ棚卸し**: playbook / lessons-learned の古い・重複エントリの統合/削除を提案する
   （`./verify.sh knowledge` が上限超過を機械検知する。超過していれば統合するか、
   統合しない理由を `KNOWLEDGE-REVIEWED` として記録する）
5. **移行対応台帳の状態**: `./verify.sh adaptation` の出力（総数・未対応件数）を提示する
6. **検出器の否定テストの結果**（CP-13）: 各観点の検出器を壊して EXIT≠0 になることを確認した記録を
   `docs/decisions/decisions.md`「否定テストの記録」に追記し、その要約を提示する。
   **人手の独立検証は Phase 境界では行わない** — 適用は**移行完了宣言**と
   **HOLD-1 の機能除外**の2つに限る（skills/migration-adversarial-review）。
   可逆な境界で残った findings は移行対応台帳に `未対応` 行として繰り越す（**件数と ID を報告に書く**）。
   どちらの記録も「実施した」だけでは規約違反（何をどう壊して何が出たか / 検証範囲を書く）

## ADR相当かどうかの判断基準（HOLD-7）

- 「この判断を将来変更するとき、コード修正1箇所で済まず波及するか？」
- 「将来の保守者が『なぜこうしたのか』と問うか？」

どちらかYesならADR相当。実例: ライブラリのパッケージング構成変更（slib統合）は一見ローカルな
ビルド修正だが、「以後の全ユーティリティは静的リンク禁止」という持続的制約を生んだ（要ADR）。
