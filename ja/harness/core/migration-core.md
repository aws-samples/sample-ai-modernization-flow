## 作業開始時に必ず行うこと

1. `<project>-migration-*/03-worklog/session-context.md` を読み、前回の状態を確認する
2. **初回セッションなら起動インタビューを行う**（下記）。2回目以降は不要
3. 現在のPhaseに応じた手順書を読む:
   - Phase 0-2: `00-analysis/analysis-procedure.md` / Phase 3以降: `01-plan/work-plan.md` の該当Step
4. `./verify.sh status` でゲートの適用状態を確認する（Phase 3以降は `./verify.sh` も実行する）

### 起動インタビュー（初回セッションのみ）

`migration-project.md` の `<PLACEHOLDER>` を**人に全部書かせない**。次の順で埋める:

1. **対象ソースを軽く走査して埋められる項目を埋める**（移行対象名・リポジトリ構成・現行スタック・
   ビルドシステム・テスト資産の所在）。深追いはしない — 構造の詳細分析は Phase 0a の ATX に委ねる
2. **埋まらない項目だけを箇条書きで1回まとめて質問する。** 小出しに聞かない
3. **記入値には出所マーカーを付ける**: `⟨confirmed⟩`（利用者が確定）/ `⟨inferred⟩`（AIの推定）。
   **`⟨inferred⟩` の値は仮説であり（CP-3）、ADR や work-plan の前提に使ってはならない**。
   必須入力は 0a-3 の前に、導出情報は work-plan 確定までに確定させる（残ると `./verify.sh project` が FAIL する）
4. **移行先スタックは未定でよい。** Phase 0b で分析結果を見てADRとして決める。
   開始に必要なのは「対象ソースのルートパス」と「off-limits」だけ

既存の ATX 分析結果があるかも**最初に**確認する（Phase 0a-0）。あれば既存結果を使う進め方に入り、
git準備・transform-config作成・ATX実行（0a-3/0a-4/0a-5）を**丸ごとスキップする**。
分析時点のコミットが不明なのが既定であり、確認で停止しない（Phase 2 の裏取りで担保 — CP-3）。

## 行動規律 — Tierゲート（自律実行の段階）

すべての作業を**後戻りコストと人の理解形成価値**に応じて3つのTier（段階）に分類する。
移行は探索的な作業であり、作業を通じて人間が理解を深めること自体が目的の一部である。
Phaseゲートはリスク管理であると同時に、人が理解を消化・形成する場である。

### Tier 0 — 自律実行ゾーン（確認不要で継続）

以下をすべて満たす作業は確認なしで実行・継続する:
- work-plan 記載済み Step 内の作業（コード修正・ビルド・テスト・調査）
- `./verify.sh` 全PASSを維持（または当該Stepで全PASSに向かう作業中）
- HOLDトリガー（下記）に該当しない

### Tier 1 — 非同期レビューゾーン（停止せず実行し、記録を残す）

以下はユーザーの指示を待たずに実行する（人は後から worklog / git log でバッチレビュー）:
- worklog / session-context の更新、知見追記（CP/DP）
- 記録系リポジトリへのコミットとpush、実装ツリーへの検証済み修正のコミット
- **Phase 3 内の Step 間の移行**: 完了報告+次Step予告+LL/CP/DP棚卸し結果を表示した上で、
  次を満たせば続行する:
  - verify 3段（build/smoke/integration）全PASS
  - **smoke ゲートが実装済み**（未実装のまま Step 2 以降に進むのは禁止。Step 1 完了時に実装）
  - HOLDトリガー非該当

### Tier 2 — 停止確認ゾーン（HOLD。停止して人の判断を仰ぐ）

以下の機械的トリガー（HOLDトリガー）に該当したら必ず停止する。自己判断で基準を緩めない:

| # | トリガー | 停止時に添える判断材料 |
|---|---------|----------------------|
| HOLD-1 | 機能の除外・無効化・スタブ化（機能喪失を伴う変更） | 除外フロー + ADRドラフト（skills/migration-adr）+ 独立検証（1件ずつの第二意見。skills/migration-adversarial-review） |
| HOLD-2 | ワイヤーフォーマット・永続化データ形式・外部公開I/Fに触る変更 | 互換性影響の分析 + ADRドラフト |
| HOLD-3 | verify.sh の期待リスト（成功基準）の変更 = スコープ変更 | 変更理由と work-plan との差分 |
| HOLD-4 | 同一問題の仮説ログが3行到達で未解決、または2セッション跨ぎ | 仮説ログ全体 + 誤診断の可能性 + サブタスク提案 |
| HOLD-5 | work-plan にない、まとまった追加作業の発生 | 「サブタスク開始: \<taskname\>」の提案 |
| HOLD-6 | 破壊的操作・共有環境への変更・**実行中の長時間ジョブ（分析・ビルド）の停止** | 実行内容と影響範囲（ユーザーに手動実行を依頼） |
| HOLD-7 | ADR相当の設計判断（選択が以後に持続的な制約を課すもの） | ADRドラフト（軽量停止プロトコル） |
| HOLD-8 | Phase境界（0a→0b→1→2→3→4）の通過 | Phase完了条件突合 + Phaseゲート定型確認 + LL/CP/DP棚卸し結果 + **検出器の否定テスト**の結果（CP-13。独立検証は**移行完了宣言と HOLD-1 の機能除外に限る**。skills/migration-adversarial-review） |

- **指示の解釈が不可逆・高コストな操作に及ぶ場合は、解釈を確認してから実行する。**
  「結果を使わない」は「生成を止めてよい」を意味しない。コスト節約・ブランチ復帰といった動機は
  エージェント側の都合であって利用者の要求ではない（善意の最適化が指示の範囲を越える典型）
- **HOLD-7 判断基準**: 「将来変更するときコード修正1箇所で済まず波及するか？」「将来の保守者が
  『なぜ』と問うか？」— どちらかYesならADR相当。**迷ったらADRを書いて止まる。多すぎは咎めない**
- **軽量停止プロトコル**: ADRドラフト（背景/選択肢/決定案/影響）を提示。ユーザーは一言で承認可。
  **判断待ちの間、依存しない別作業には進んでよい**。保留判断は session-context の Decision Queue で管理
- HOLD-1 除外フロー / HOLD-8 Phaseゲート定型確認の詳細: **skills/migration-adr** を参照
- Tier 2（HOLD）が多発する場合（1 Stepで3回以上）は基準過広のサイン。調整をユーザーに提案する

### モデルの割り当て（Tier に沿って変える）

**分けるのは「主/従」ではなく「判断/量」である。サブエージェントだから軽いモデル、ではない。**

| 対象 | 支配的な性質 | 割り当て |
|------|------------|---------|
| Tier 0 の作業（work-plan 内の実装・ビルド・テスト・調査） | 量 | 速いモデルで可 |
| Tier 1 の作業（worklog・記録・コミット・和訳・台帳転記） | 量 | **速いモデル推奨** |
| **Tier 2（HOLD）全般・ADR判断・HOLD-1除外・work-plan確定・独立検証** | 判断 | **強いモデルを維持する** |

独立検証のサブエージェントは判断をしているので強いモデル、和訳バッチは速いモデルである。
**移行の事故は「速く大量に書けなかった」ではなく「一次情報との食い違いに気づけなかった」で起きる。**
モデルを落とすなら、落とす対象が判断を含まないことを先に確認する。

## 作業品質ルール（常時適用）

1. **AI分析結果は仮説。** 実コードで裏取りしてから計画に含める（CP-3）
2. **ビルド成功 ≠ 修正完了。** 実行時テストで観測するまで完了と宣言しない（CP-4）
3. **修正前に「何を観測すれば正しいか」を定義する**（CP-4）
4. **1つ修正したら最終成功まで再検証する**（CP-2）
5. **プラットフォーム依存の設定値は一次情報（公式ドキュメント・man等）で裏取りする**（該当Playbookのpractices.md参照。例: clang Playbook の DP-8）
6. **crash・失敗は実行コマンド・環境・終了コードを必ず確認する**（例: 124=timeout生存、139=SIGSEGV、127=lib不足）
7. **根本原因は因果の実証をもって確定する**（CP-8）。原因のON/OFFで症状が再現/消失するまで「仮説」と書く
8. **長時間コマンド（ATX実行・大規模ビルド等）はAIが実行しログ監視する。**単純な生存監視ループだけに頼らない（詳細: skills/migration-troubleshooting）

### 仮説ログ（トラブルシュート時に必須）

修正試行のたびに1行記録する（小規模=worklog、サブタスク=investigation.md）:

| # | 仮説 | 予測（この修正で何が変わるはず） | 観測結果 | 判定（解決/棄却/継続） |
|---|------|--------------------------------|---------|---------------------|

記録せずに試行することは記録義務違反。詳細: **skills/migration-troubleshooting**

### 中断耐性（着手時に宣言する）

記録義務は作業完了時に発火するため、中断された作業を守れない。よって:
1. **最初の変更の前に**、`03-worklog/session-context.md` の「In-progress Investigation /
   Working-tree State」節に `- **This turn (<時刻>):** <何をやろうとしているのか>` を1行書く。
   work-plan 内の作業でも書く。**`<時刻>` は毎ターン `./03-worklog/turn-report.sh --declare` を
   実行し出力をそのまま使う。手入力・前ターン値の再利用/近似は禁止**（guard が1文字単位で照合しブロックする）
2. **進行中の状態を未コミット作業ツリーだけに残さない**: 実装ツリーに `[wip]`/`[diag]` を小刻みにコミットし、
   使い捨ての診断コードには `// DIAG-<id>:` を付けて後で除去できるようにする
3. **完了時は宣言行と仮説ログを worklog へ写す**（写さないと恒久記録に残らない）

詳細: **skills/migration-troubleshooting**

## 記録の義務

作業の各単位（調査・修正・テスト）の完了時に必ず行う。行うまで「完了」と宣言しない:
1. `03-worklog/worklog.md` に追記（時系列順・末尾追記）。追記後に
   **`./03-worklog/turn-report.sh --worklog` を実行して出力をそのエントリに貼る**（生ログは git-ignored）。
   **表の手書き・模写は禁止。数値は必ずコマンド出力そのまま**
2. `03-worklog/session-context.md` を更新（Current Status / Next Actions / Verification Queue / Decision Queue）
3. Phase/Step・サブタスク・Tier 2（HOLD）対応の完了時はLL/CP/DP棚卸しを行う（該当なしも明示）

フォーマット詳細（コミットメッセージ、知見追記、棚卸しタイミング）: **skills/migration-recording**

### 知見の参照粒度と量（コンテキストを小さく保つ）

- **知見ファイル（practices-common.md / practices.md）は既定でサマリ表だけを読む。**
  本文は該当テーマに当たったときに開く。本文は人が読んで理解するための層であり、詳しくてよい
- **`worklog.md` は時系列で読まない。** 前回状態の把握は `session-context.md` から行う
- **無印の `CP-N` / `DP-N` をプロジェクト側で採番しない**（`CP-<project>-N` / `DP-<project>-N` を使う）
- 量の上限（サマリ行・本文行数・エントリ数）は `./verify.sh knowledge` が機械検査する。
  上限超過は統合のトリガーであり、統合しない判断は記録すれば通る

### 一時的な変更のマーカー（機械検知される）

一時的にしか存在してはならない変更には、コミット前に必ずマーカーを付ける。
`./verify.sh repo-sync` がコミット済みコードに残ったマーカーを FAIL として検出する:

| マーカー | 用途 | 解消の条件 |
|---------|------|-----------|
| `// DIAG-<id>:` | 使い捨ての診断コード | 原因確定後に revert する |
| `// STUB-<id>:` | 一時的なスタブ・モック・機能の無効化 | 実装を入れる。恒久的な除外なら HOLD-1 として ADR を書き、移行対応台帳の処理区分を「対応不要（理由必須）」にする |

**「意図せず機能をモック化して最後まで気づかない」事故を機械で塞ぐための仕組みである。**
Playbook が定義する禁止パターン（`not implemented` 等）も同じゲートで検査される。

## 検証ゲート

- `./verify.sh` 全PASSまで「完了」と記録しない。**全8ゲート**:
  - work-plan 確定で適用が切り替わる4段: build（成果物存在）→ smoke（起動）→
    integration（連携・golden-path E2E）+ opt-in時 nonfunc（非機能）
  - **常時適用の4段**: repo-sync（2リポジトリ同期・診断/スタブマーカー）→
    knowledge（知見の量）→ adaptation（移行対応台帳）→ project（出所マーカー）
- 適用状態は `./verify.sh status` で確認できる
- **スコープ内全成果物を work-plan 確定時（初日）に期待リストへ登録**（CP-7。未ビルドでも登録）
- アドホック検証は `02-test/integration/` に昇格し integration ゲートから呼ぶ
- 詳細・テスト記録のルール: **skills/migration-verification**

## サブタスク

ユーザーが「サブタスク開始: \<taskname\>」と指示、またはHOLD-4/HOLD-5で提案が承認された場合、
**skills/migration-subtask** の手順に従う。作業ファイルは全てサブタスクディレクトリ内に置く。

## セッション終了チェックリスト（Tier 1・非同期レビューゾーン — 指示を待たず実行）

セッション終了時は指示を待たずに実行する。**片方のリポジトリだけのコミット・pushは未完了**:
1. worklog 追記確認 → 2. session-context 更新（リポジトリ同期状態テーブル含む）
3. 記録系リポジトリをクリーンまでコミット → 4. 実装ツリーの検証済み変更をコミット
5. リモートがあれば両方 push → 6. 両リポジトリの `git log --oneline -1` と `git status --short` を報告
詳細: **skills/migration-session**

## Off-limits・プロジェクト固有情報

`migration-project.md`（Kiro: `.kiro/steering/` / Claude Code: `CLAUDE.md` 冒頭）を参照。

**対象ソースは内容を変更しない**（履歴の初期化は許可）。作業は実装ツリー側で行う
（skills/migration-tree-setup）。対象ソースに対して許可される git 操作は次の3つのみ:

- `git init` / 初期コミット / `.gitignore` 追加（ATX が git 管理を要求するため）
- 禁止: remote 追加 / push / reset / rebase / ブランチ削除 / force 系。迷ったら HOLD-6

ATX 実行は対象リポジトリに書き込む（`.gitignore` 追記・staging ブランチ作成・コミット）。
**実行前のブランチと HEAD を記録し、実行後に一致を確認する**（記録先: `00-analysis/analysis-runs.md`）。
